내적

JAVA두 배열을 같은 인덱스로누적 합int 범위

한 줄 요약길이가 같은 두 배열 a · b를 같은 인덱스로 돌며 a[i] * b[i]를 모두 더한다. 합의 최댓값이 10억이라 int로 충분하다.

쉽게 말하면장바구니 영수증이에요. 한 줄에는 수량, 다른 줄에는 단가가 같은 순서로 적혀 있으면 같은 줄끼리 곱해서 전부 더하면 총액이 나옵니다. 그게 내적이에요.

🔗 프로그래머스에서 문제 보기

길이가 같은 두 1차원 정수 배열 a, b의 내적 a[0]*b[0] + a[1]*b[1] + … + a[n-1]*b[n-1]을 반환하는 문제. 길이는 1 이상 1,000 이하, 원소는 −1,000 이상 1,000 이하. [1,2,3,4] · [-3,-1,0,2] → 3.

📄 제출 코드 파일 · 📁 25회차 전체 기록

JAVA 제출 코드 · 오답노트 원문 (PASS) 
class Solution {
    public int solution(int[] a, int[] b) {
        int answer = 0;

        for(int i=0;i<a.length;i++){
            answer = answer+a[i]*b[i];        // ← 같은 i 끼리 곱해서 누적
        }

        return answer;
    }
}
💡 정답 풀이

제출 코드가 정답이다. 오답노트에는 정답 풀이·개념 정리 칸이 비어 있어, 아래는 이 문제에서 짚어 둘 점이다. 더 짧게 쓰는 법 1. answer = answer + a[i]*b[i] → answer += a[i] * b[i] — 복합 대입 연산자. 뜻은 같다. 2. 스트림으로 한 줄 — IntStream.range(0, a.length).map(i -> a[i] * b[i]).sum(). 코딩테스트에서는 for문이 더 빠르고 읽기도 쉽다. 흔히 틀리는 곳 1. 향상된 for문(for (int x : a)) — 인덱스가 없어 짝이 되는 b[i]를 찾을 수 없다. 24회차 음양 더하기와 같은 이유다. 2. 범위 걱정 — 원소가 최대 1,000이고 1,000개라 합은 −10억 ~ 10억. int의 최댓값(약 21억) 안이라 long이 필요 없다. 원소나 길이가 조금만 커져도 넘치니 최댓값을 먼저 계산해 보는 습관이 중요하다(23회차 콜라츠 추측).

공식 예제 [1,2,3,4] · [-3,-1,0,2]  → 3
공식 예제 [-1,0,1]  · [1,0,-1]     → -2              → 통과

가장 큰 / 작은 합 (1000 × 1000 × 1000개)            → 1,000,000,000 / -1,000,000,000 (int 최댓값 2,147,483,647 안)
기댓값은 long으로 더하는 별도 코드로 만들었어요(시드 25 고정). 로컬 검증이며 프로그래머스 재채점은 아닙니다.

🤔 스스로 확인

답을 펼치기 전에 머릿속으로 먼저 대답해 보세요. 오답노트는 다시 떠올려 봐야 내 것이 됩니다.

원소 범위가 -100,000 ~ 100,000 이고 길이가 1,000이면 int 로 충분할까?
부족합니다. 한 곱이 최대 100억(1010)이라 곱 하나부터 int를 넘어요. answer를 long으로 바꾸는 것만으로는 안 되고, 곱하기 전에 (long) a[i] * b[i]처럼 한쪽을 먼저 long으로 바꿔야 합니다(int끼리 곱한 결과가 이미 넘친 뒤에 long에 담기면 늦어요).
예제 2([-1,0,1] · [1,0,-1])를 손으로 계산하면?
(−1)×1 + 0×0 + 1×(−1) = −1 + 0 − 1 = −2. 음수끼리 곱하면 양수, 음수 × 양수는 음수라는 것만 지키면 됩니다.

💼 이 유형을 다시 만나면내적은 "같은 줄끼리 곱해서 더하기"라 실무에서는 수량 × 단가 합계, 점수 × 가중치 합계로 자주 나와요. 머신러닝에서도 벡터 유사도의 기본 연산입니다. 코드는 쉬우니 합의 범위만 먼저 따져 보세요.

원문의 제출 코드 칸에는 이 문제의 코드가 아니라 24회차 올바른 괄호의 제출 코드(boolean solution(String s), 스택)가 공백만 다르고 그대로 들어 있다. 이 문제의 함수 모양(int[] solution(int[] progresses, int[] speeds))과 달라서 기능개발 제출본으로 보지 않았고, 실패 원인도 단정하지 않았다. 아래는 원문에 적힌 두 가지 정답 풀이다.

JAVA 정답 풀이 1 — 큐 (오답노트 원문) 
Queue<Integer> queue = new LinkedList<>();
for (int i = 0; i < progresses.length; i++) {
    int remain = 100 - progresses[i];
    int days = (remain % speeds[i] == 0) ? (remain / speeds[i]) : (remain / speeds[i] + 1);  // ← 올림
    queue.offer(days);                       // ← 끝나는 날을 순서대로 줄 세우기
}

List<Integer> resultList = new ArrayList<>();
int maxDay = queue.poll();                   // ← 첫 작업이 첫 묶음의 기준일
int count = 1;
while (!queue.isEmpty()) {
    int currentDay = queue.poll();
    if (currentDay <= maxDay) {
        count++;                             // ← 기준일 안에(또는 같은 날) 끝남 → 함께 배포
    } else {
        resultList.add(count);               // ← 더 늦게 끝남 → 지금 묶음 확정
        maxDay = currentDay;                 //   새 기준일
        count = 1;
    }
}
resultList.add(count);                       // ← 마지막 묶음 (빠뜨리기 쉽다)
// ArrayList → int[]
int[] answer = new int[resultList.size()];
for (int i = 0; i < resultList.size(); i++) answer[i] = resultList.get(i);
return answer;
JAVA 정답 풀이 2 — 큐 없이 반복문 하나 (오답노트 원문) 
int maxDay = 0, count = 0;
for (int i = 0; i < progresses.length; i++) {

💡 정답 풀이

풀이의 세 단계 1. 끝나는 날 = 올림 나눗셈 — 남은 양 100 - progresses[i]을 속도로 나눠 나머지가 조금이라도 있으면 하루 더. 예제 1의 30%짜리 작업은 70 ÷ 30 = 2.33… → 3일. 2. 기준일로 묶기 — 앞 작업 중 가장 늦게 끝나는 날(maxDay)이 뒤 작업의 배포일을 정한다. days <= maxDay면 같은 묶음(count++), 더 크면 지금 묶음을 확정하고 새 기준일. 예제 1은 끝나는 날이 [7, 3, 9] → 3은 7 안이라 함께(2개), 9는 7보다 늦어 새 묶음(1개) → [2, 1]. 3. 마지막 묶음 — 묶음은 "더 늦은 작업을 만났을 때"만 확정되니, 반복이 끝난 뒤 들고 있던 묶음을 한 번 더 넣는다. 흔히 틀리는 곳 1. Math.ceil(remain / speed) — int / int가 먼저 버림된 뒤 올림하니 소용없다. 가능한 9,900쌍 중 9,427쌍에서 하루 적게 나왔다(예: 7/3 → 2, 맞는 값 3). (double) remain / speed처럼 나누기 전에 실수로 바꾼다. 2. <=를 <로 — 같은 날 끝나는 뒤 작업도 함께 나가야 한다. <로 쓰면 [99,99] · [1,1](둘 다 1일)이 [1, 1]로 갈린다(정답 [2]). 무작위 50,000개 중 29,680개가 틀렸다. 3. 마지막 resultList.add(count) 빠뜨림 — 예제 1 → [2], 예제 2 → [1, 3], 작업이 하나뿐이면 [].

(1) 스택(LIFO)과 큐(FIFO) 스택은 나중에 넣은 것이 먼저(push · pop · peek, 접시 쌓기), 큐는 먼저 넣은 것이 먼저(offer · poll · peek, 줄 서기). 자바에서 큐는 Queue<Integer> q = new LinkedList<>();(또는 ArrayDeque). 비었을 때 poll()은 null, remove()는 예외. → 올바른 괄호(스택) · 🛠️ 02. List 계열 (2) 정수 올림 나눗셈 세 가지 (r % s == 0) ? r / s : r / s + 1 · (r + s - 1) / s · (int) Math.ceil((double) r / s). 마지막은 (double)을 나누기 전에. 페이지 수 계산(ceil(count/10))과 같은 계산이다. → 41일차 페이징 (3) 기준값으로 연속 구간 묶기 "앞에서 정한 기준보다 큰 값이 나오면 끊는다" — 묶음은 끊을 때 확정되니 끝에서 한 번 더 확정한다. (4) ArrayList → int[] 답의 개수를 미리 모를 때 리스트에 모아 마지막에 배열로. 반복문으로 옮기거나 list.stream().mapToInt(Integer::intValue).toArray().

예제 2 ([95,90,99,99,80,99] · 속도 모두 1)의 끝나는 날과 묶음을 손으로 구하면?

방법 2에서 maxDay를 0, count를 0으로 시작하고 if (count > 0)을 둔 이유는?
끝나는 날은 최소 1일이라 첫 작업은 반드시 days > 0이 되어 새 묶음을 시작해요. 그때 아직 확정할 묶음이 없으니(count == 0) 빈 묶음 0이 들어가지 않게 if (count > 0)으로 막습니다. 방법 1은 첫 작업을 poll()로 미리 꺼내 같은 문제를 피했어요.

답을 펼치기 전에 머릿속으로 먼저 대답해 보세요. 오답노트는 다시 떠올려 봐야 내 것이 됩니다.

CASE WHEN FREEZER_YN IS NULL THEN 'N' END 만 쓰면 'Y' 인 창고는 무엇으로 나올까?
NULL로 나와요. 'Y'는 IS NULL에 맞지 않고, 다른 WHEN도 ELSE도 없으니 CASE가 기본값 NULL을 돌려줍니다. 문제는 "NULL만 바꿔라"인데 오히려 정상 값을 지운 셈이에요.
냉동시설 여부가 NULL이면 'N', 그런데 FREEZER_YN 대신 FREEZER_YN2 라는 예비 컬럼을 먼저 보고 싶다면?
COALESCE(FREEZER_YN2, FREEZER_YN, 'N')처럼 후보를 순서대로 나열합니다. 앞에서부터 처음 나오는 NULL 아닌 값을 돌려주니, 둘 다 NULL일 때만 'N'이 돼요. IFNULL은 인자가 두 개뿐이라 이렇게는 못 씁니다.

💼 이 유형을 다시 만나면"값이 없으면 기본값으로 보여 주기"는 리포트 · 화면 조회의 단골이에요(미입력 연락처 → '-', 미정 상태 → '대기'). 실무에서는 DB 쪽에서 COALESCE로 처리하거나, 처음부터 컬럼에 NOT NULL DEFAULT 'N'을 걸어 NULL이 생기지 않게 합니다. 코딩테스트에서는 CASE를 쓰면 ELSE부터 챙기세요.

SQL 제출 코드 · 오답노트 원문 (PASS) 
select ID, case when SIZE_OF_COLONY <= 100 then 'LOW'
when SIZE_OF_COLONY > 100 and SIZE_OF_COLONY <= 1000 then 'MEDIUM'   -- ← "> 100" 은 없어도 된다
when SIZE_OF_COLONY > 1000 then 'HIGH' end as SIZE                   -- ← ELSE 'HIGH' 로 충분
from ECOLI_DATA
order by ID asc;

    ID,

💡 정답 풀이

제출 코드도 정답이다. 원문에는 "더 간결하게 다듬은 정석 코드"가 함께 적혀 있다. 왜 줄일 수 있나 — CASE는 위에서부터 CASE는 WHEN을 위에서부터 검사해 처음 참인 것 하나만 고르고 나머지는 보지 않는다. 두 번째 WHEN에 도착했다면 첫 번째(<= 100)가 거짓이었다는 뜻이라 > 100 and는 저절로 성립한다. 마지막 구간도 남은 전부라 ELSE 'HIGH'. 흔히 틀리는 곳 1. 경계값 — "100 이하"는 <= 100. < 100으로 쓰면 크기 100이 MEDIUM, 1000이 HIGH로 한 칸씩 밀린다(실행으로 확인). 2. WHEN 순서 — <= 1000을 먼저 쓰면 100 이하도 먼저 맞아 전부 MEDIUM이 된다. 줄인 코드는 순서에 기대고 있으니 작은 구간부터 쓴다. 3. ELSE 없이 끝 조건만 — 제출 코드처럼 > 1000을 WHEN으로 쓰면 괜찮지만, 값이 NULL이면 어느 WHEN에도 안 맞아 NULL이 된다. 이 문제는 SIZE_OF_COLONY가 NULL을 허용하지 않아 상관없다(식품창고의 ELSE 함정과 같은 규칙).
