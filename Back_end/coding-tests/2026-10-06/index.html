서울에서 김서방 찾기

JAVA문자열 비교 equals배열 순회문자열 연결

한 줄 요약배열을 처음부터 돌며 "Kim"과 equals로 같은 칸을 찾고, 그 인덱스를 "김서방은 x에 있다" 문장에 끼워 돌려준다.

쉽게 말하면출석부를 위에서부터 읽다가 "Kim"이라는 이름이 나오면 몇 번째 줄인지 적어 내는 일이에요. 이름이 같은지는 글자가 같은지(equals)로 봐야 합니다.

🔗 프로그래머스에서 문제 보기

문자열 배열 seoul(길이 1~1,000)에 "Kim"이 딱 한 번 들어 있다. 그 위치(인덱스) x를 찾아 "김서방은 x에 있다"를 반환하는 문제.

📄 제출 코드 파일 · 📁 22회차 전체 기록

JAVA 제출 코드 · 오답노트 원문 (PASS) 
class Solution {
    public String solution(String[] seoul) {
        String answer = "김서방은 ";
        for(int i =0;i<seoul.length;i++){
            if(seoul[i].equals("Kim")){                              // ← == 가 아니라 equals
                answer = answer+(Integer.toString(i))+"에 있다";      // ← 찾은 뒤에도 끝까지 돈다
            }
        }
        return answer;
    }
}
💡 정답 풀이

제출 코드가 정답이다. 오답노트에는 정답 풀이·개념 정리 칸이 비어 있어, 아래는 이 문제에서 짚어 둘 점이다. 흔히 틀리는 곳 1. seoul[i] == "Kim"으로 비교 — ==는 두 변수가 같은 객체인지 본다. 채점 입력이 리터럴이면 우연히 맞을 수 있지만, 실행 중에 만들어진 문자열이면 글자가 같아도 false다. 문자열 내용 비교는 언제나 equals. 2. 문장 형식 — "김서방은 1에 있다"에서 띄어쓰기 하나만 달라도 오답이다. 문제의 출력 예시를 그대로 복사해 쓰는 습관이 안전하다. 더 짧게 쓰는 방법 "Kim"은 한 번만 나오므로 찾는 즉시 return "김서방은 " + i + "에 있다";로 끝내도 된다(뒤를 더 볼 필요가 없다). 문자열과 숫자를 +로 이으면 Integer.toString(i) 없이도 숫자가 글자로 바뀐다. Arrays.asList(seoul).indexOf("Kim")도 같은 위치를 돌려준다(indexOf는 안에서 equals로 비교).

실행 결과== 와 equals 를 직접 비교 먼저 예측 → 펼쳐서 확인 
공식 예제 ["Jane", "Kim"]          → 김서방은 1에 있다
무작위 20,000개 (길이 1~1000)       → 모두 통과
new String("Kim") == "Kim"          → false
new String("Kim").equals("Kim")     → true
실행 중에 이어 붙인 "Ki"+'m' == "Kim" → false
리터럴 "Kim"은 String pool의 객체 하나를 함께 쓰지만, new나 실행 중 연결로 만든 문자열은 새 객체입니다. 글자가 같아도 ==는 false예요.

(3) 문자열 + 숫자 "김서방은 " + i처럼 한쪽이 문자열이면 다른 쪽은 자동으로 문자열로 바뀐다. 다만 반복문 안에서 문자열을 계속 이어 붙이면 매번 새 객체가 생기니 그럴 땐 StringBuilder. → 📖 String vs StringBuilder

답을 펼치기 전에 머릿속으로 먼저 대답해 보세요. 오답노트는 다시 떠올려 봐야 내 것이 됩니다.

제출 코드에서 equals를 ==로 바꿔도 프로그래머스에서 통과할 수 있는 이유와, 그래도 쓰면 안 되는 이유는?
채점 입력의 "Kim"이 코드 속 리터럴과 같은 pool 객체라면 ==도 우연히 true가 됩니다. 하지만 입력이 파일·네트워크·new String에서 왔다면 글자가 같아도 다른 객체라 false예요. "우연히 맞는 코드"는 환경이 바뀌면 깨지므로 내용 비교는 항상 equals입니다.
"Kim"이 두 번 들어 있다면 제출 코드는 무엇을 돌려줄까?
찾을 때마다 문장 뒤에 덧붙이므로 "김서방은 1에 있다3에 있다"처럼 이상한 문장이 됩니다. 문제 조건(딱 한 번)이 있어서 괜찮았던 것이고, 찾는 즉시 return하면 첫 위치만 돌려줘 더 안전해요.
seoul[i].equals("Kim")과 "Kim".equals(seoul[i]) 중 더 안전한 쪽은?
"Kim".equals(seoul[i])입니다. 배열 칸이 null이면 앞쪽은 null.equals(…)라 NullPointerException이 나지만, 리터럴을 앞에 두면 false로 끝나요. 이 문제는 null이 없지만 실무 코드에서 자주 쓰는 습관입니다.

💼 이 유형을 다시 만나면"배열에서 값 하나 찾기"는 코딩테스트 입문 문제의 단골이고, 실무에서도 문자열 비교를 ==로 한 버그는 코드 리뷰에서 가장 먼저 지적됩니다. 면접에서 "String을 ==로 비교하면 왜 안 되나요?"가 나오면 String pool과 new String의 차이를 예로 들어 설명하면 됩니다.

체육복

JAVA탐욕법 Greedy상태 배열경계 패딩향상된 for문

한 줄 요약학생마다 가진 체육복 수(0·1·2)를 한 배열에 담고, 1번부터 차례로 0벌인 학생이 앞 번호 → 뒤 번호 순으로 여벌을 빌린다. 배열을 n+2로 잡아 양 끝 경계 검사를 없앤다.

쉽게 말하면줄 선 학생들 중 체육복이 없는 아이는 앞사람에게 먼저 빌립니다. 앞사람의 여벌은 지금 아니면 쓸 데가 없지만, 뒷사람의 여벌은 그 뒤 아이가 필요할 수도 있으니까요. 도난당한 아이가 여벌도 가져왔다면 그 여벌은 자기가 입습니다.
❌ FAILJAVA22회차 · 2026.10.06
🔗 프로그래머스에서 문제 보기

학생 n명(2~30) 중 체육복을 도난당한 학생 번호 lost, 여벌을 가져온 학생 번호 reserve가 주어진다. 여벌은 바로 앞·뒤 번호에게만 빌려줄 수 있고, 여벌을 가져온 학생이 도난당했다면 그 학생은 남에게 빌려줄 수 없다. 체육 수업을 들을 수 있는 최대 인원을 구하는 문제. lost·reserve가 정렬돼 있다는 보장은 없다.

📄 정답 풀이 파일 · 📁 22회차 전체 기록

JAVA 정답 풀이 (오답노트 원문 · 제출 코드는 남아 있지 않음) 
class Solution {
    public int solution(int n, int[] lost, int[] reserve) {
        int[] student = new int[n+2];                     // ← 0번·n+1번은 경계용 빈 칸
        for (int i = 1; i <= n; i++) student[i] = 1;     // ← 모두 1벌로 시작
        for (int l : lost) student[l]--;                  // ← 도난: -1
        for (int r : reserve) student[r]++;               // ← 여벌: +1 (도난+여벌이면 1로 돌아온다)

        for(int i=1;i<=n;i++){
            if( (student[i]==0) && (student[i-1]==2) ){        // ← 앞 번호 먼저
                student[i]++;
                student[i-1]--;
            }else if( (student[i]==0) && (student[i+1]==2) ){  // ← 그다음 뒤 번호
                student[i]++;
                student[i+1]--;
            }
        }

        int count=0;
        for(int i=1;i<=n;i++){
           if(student[i] >= 1){                           // ← 빌려주지 못해 2벌인 학생도 포함
                count++;
            }
        }
        return count;
    }
}
💡 정답 풀이

제출 코드 칸이 비어 있어 실제로 어디서 틀렸는지는 알 수 없다. 아래는 이 문제에서 흔히 틀리는 곳과 정답 풀이의 흐름이다. 흔히 틀리는 곳 1. 도난당한 여벌 학생을 빼지 않기 — lost와 reserve 배열을 그대로 비교하면, 도난당한 여벌 학생이 남에게 빌려준 것처럼 계산된다. n=2, lost=[1], reserve=[1]의 답은 2인데 1이 나온다. 2. 뒤 번호부터 빌리기 — 뒤 학생의 여벌을 먼저 가져오면, 그 뒤에 0벌인 학생이 빌릴 곳이 없어진다. n=4, lost=[2,4], reserve=[1,3]은 앞 먼저면 4명, 뒤 먼저면 3명. 3. 정렬되지 않은 입력 — lost를 그대로 순서대로 처리하면 순서에 따라 답이 달라진다. 학생 번호 칸 배열을 쓰면 1번부터 차례로 보므로 입력 순서와 상관없다. 4. 경계 — 1번의 앞(0번), n번의 뒤(n+1번)를 볼 때 ArrayIndexOutOfBoundsException. 배열을 n+2로 잡거나 if (i > 1) 같은 조건을 넣는다. 풀이 흐름 1. 학생마다 체육복 수를 담는 배열을 n+2 크기로 만들고 1~n번을 1로 채운다. 2. 도난은 −1, 여벌은 +1. 도난+여벌 학생은 1 − 1 + 1 = 1로 저절로 "빌려줄 수 없는 평범한 상태"가 된다. 3. 1번부터 차례로, 0벌이면 앞 번호가 2벌일 때 먼저 빌리고, 아니면 뒤 번호에게 빌린다. 4. 1벌 이상인 학생을 센다.

실행 결과흔한 실수 두 가지를 실제로 돌려 보면 먼저 예측 → 펼쳐서 확인 
공식 예제 3개                                         → 통과 (5 · 4 · 2)
n 2~8 에서 가능한 입력 전부 86,367개 (lost 순서는 섞음) → 모두 통과
흔한 실수 ① 뒤 번호부터  n=4, lost=[2,4], reserve=[1,3] → 정답 4 / 뒤 먼저 3
흔한 실수 ② 도난당한 여벌 무시  n=2, lost=[1], reserve=[1] → 정답 2 / 무시하면 1
n=5, lost=[2,4], reserve=[3]                          → 4 (3번의 여벌은 앞 번호 2번이 먼저 받는다)
기댓값은 여벌 학생마다 "앞에게 / 뒤에게 / 안 빌려줌"을 전부 시도해 최댓값을 구하는 별도 코드로 계산했습니다. 그 최댓값과 정답 풀이가 86,367개 입력에서 모두 같았어요 — 앞 번호 먼저라는 탐욕 규칙이 언제나 최선이라는 뜻입니다.
📌 주요 개념 정리

(1) 탐욕법(Greedy) 매 순간 가장 좋아 보이는 선택을 이어 가는 방법이다. 이 문제에서는 "0벌이면 앞 번호에게 먼저"가 그 선택이고, 앞 학생의 여벌은 지나가면 다시 쓰일 일이 없기 때문에 이 선택이 손해를 보지 않는다. 탐욕법은 그 선택이 왜 손해가 없는지 설명할 수 있을 때만 쓴다. (2) 상태를 한 배열로 — 경계 패딩 두 배열(lost·reserve)을 서로 비교하는 대신, 학생별 체육복 수라는 하나의 상태 배열로 합치면 조건문이 크게 줄어든다. 앞뒤 칸(i-1, i+1)을 보는 문제는 양 끝에 빈 칸을 덧대 n+2로 잡으면 경계 조건을 따로 쓸 필요가 없다. (3) 향상된 for문 vs 일반 for문 for (int l : lost) student[l]--;는 배열의 값을 하나씩 꺼낸다 — 처음부터 끝까지 읽기만 할 때 짧고 인덱스 실수가 없다. 인덱스 자체가 필요하거나 앞뒤 칸을 비교할 때(student[i-1])는 일반 for문을 쓴다. → 🧱 17. 향상된 for문

🤔 스스로 확인

답을 펼치기 전에 머릿속으로 먼저 대답해 보세요. 오답노트는 다시 떠올려 봐야 내 것이 됩니다.

배열을 new int[n]으로 잡고 학생 번호를 그대로 인덱스로 쓰면 어떤 문제가 생길까?
학생 번호는 1~n인데 배열 인덱스는 0~n−1이라 n번 학생에서 ArrayIndexOutOfBoundsException이 나고, 앞뒤를 볼 때 0번·n+1번도 범위 밖입니다. 번호를 그대로 인덱스로 쓰고 경계 검사도 없애려고 n+2로 잡은 거예요.
도난당했지만 여벌을 가져온 학생이 정답 풀이에서 자동으로 처리되는 이유는?
기본 1벌에서 도난으로 −1, 여벌로 +1을 하면 1이 됩니다. 빌려주는 조건은 "2벌"이므로 이 학생은 남에게 빌려주지 않고 자기 것만 입어요. 두 배열을 따로 비교했다면 "lost에도 reserve에도 있는 학생을 먼저 빼는" 코드가 필요했을 겁니다.
마지막에 student[i] == 1이 아니라 >= 1로 세는 이유는?
여벌이 있었지만 빌려줄 사람이 없어 2벌로 남은 학생도 수업을 들을 수 있기 때문입니다. == 1로 세면 그 학생들이 빠져 인원이 적게 나와요.

💼 이 유형을 다시 만나면"이웃에게만 줄 수 있다 + 최대 몇 명" 꼴은 탐욕법 입문의 대표 유형입니다. 탐욕법이 맞는지 확신이 없을 때는 이번처럼 작은 입력에서 모든 경우를 시도하는 코드와 답을 비교해 보면 확인할 수 있어요. 실무의 자원 배정(회의실·좌석 배정 등)에서도 "지금 쓰지 않으면 버려지는 것부터 먼저 쓴다"는 같은 생각을 씁니다.

동물 보호소 테이블 ANIMAL_INS에서 가장 먼저 들어온 동물의 이름을 조회하는 문제. DATETIME이 보호 시작일이다.

📄 정답 풀이 파일 · 📁 22회차 전체 기록

SQL 정답 풀이 (오답노트 원문 · 제출 코드는 남아 있지 않음) 
SELECT NAME
FROM ANIMAL_INS
ORDER BY DATETIME ASC     -- ← 과거 → 최근 (가장 이른 날짜가 맨 위)
LIMIT 1;                  -- ← 맨 위 한 행만
💡 정답 풀이

제출 코드 칸이 비어 있어 실제로 어디서 틀렸는지는 알 수 없다. 아래는 이 문제에서 흔히 틀리는 곳이다. 흔히 틀리는 곳 1. ORDER BY 없이 LIMIT 1 — 정렬하지 않은 결과의 "첫 행"은 저장 순서 등에 따라 정해질 뿐 가장 먼저 들어온 동물이라는 보장이 없다. 2. DESC로 정렬 — 내림차순은 가장 최근에 들어온 동물이 맨 위에 온다. 3. SELECT NAME, MIN(DATETIME) — 집계 함수와 일반 컬럼을 섞으면 MIN은 가장 이른 날짜를 주지만 NAME은 그 행의 이름이라는 보장이 없다(설정에 따라 오류가 나거나 아무 행의 이름이 나온다). 그 날짜를 가진 행을 원하면 정렬 + LIMIT이나 서브쿼리 WHERE DATETIME = (SELECT MIN(DATETIME) …). 4. 절 순서 — LIMIT은 맨 끝, ORDER BY보다 뒤에 쓴다.

실행 결과보호 시작일이 다른 동물 4마리로 먼저 예측 → 펼쳐서 확인 
정답 풀이 (ORDER BY DATETIME ASC LIMIT 1)   → Jack   (2013-10-14, 가장 이른 날짜)
정렬 없이 LIMIT 1                           → Lucy   (먼저 넣은 행 — '가장 먼저 들어온' 동물이 아님)
ORDER BY DATETIME DESC LIMIT 1               → Max    (2016-01-01, 가장 최근)
SQL 파일을 그대로 읽어 Node 내장 SQLite(메모리 DB)에서 실행했습니다. ORDER BY · LIMIT은 MySQL과 같은 규칙이에요.
📌 주요 개념 정리

(1) 정렬 → 자르기 "가장 ○○한 n개"는 언제나 기준으로 정렬한 뒤 LIMIT n이다. ASC는 작은 값(과거) → 큰 값(최근), DESC는 반대. → 🗄️ 15. ORDER BY (2) 쓰는 순서와 처리되는 순서는 다르다 쓰는 순서는 SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT이지만, DB가 논리적으로 처리하는 순서는 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT이다. 그래서 WHERE에서는 SELECT에서 붙인 별칭을 못 쓰고, ORDER BY에서는 쓸 수 있다. (3) DBMS마다 다른 "상위 n개" MySQL·MariaDB·PostgreSQL은 LIMIT n, SQL Server는 SELECT TOP n, Oracle은 FETCH FIRST n ROWS ONLY(12c부터) 또는 ROWNUM. 프로그래머스 SQL 문제는 MySQL 문법이 기본이다.

⚠️ 오답노트 표현 바로잡기

오답노트의 개념 정리는 SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT을 "실행 및 작성 순서"로 함께 적었는데, 이것은 작성 순서입니다. 실행(논리 처리) 순서는 FROM이 맨 처음이고 SELECT는 HAVING 다음이에요(위 개념 (2)). "ORDER BY가 LIMIT보다 먼저"라는 결론은 두 순서 모두에서 맞습니다.

답을 펼치기 전에 머릿속으로 먼저 대답해 보세요. 오답노트는 다시 떠올려 봐야 내 것이 됩니다.

"가장 늦게 들어온 동물 3마리의 이름"으로 바꾸면 어디를 고칠까?
ORDER BY DATETIME DESC LIMIT 3으로 정렬 방향과 개수를 바꿉니다. 정렬 기준이 같으면 "가장 이른"은 ASC, "가장 늦은"은 DESC예요.
SELECT NAME AS 이름 … 다음에 WHERE 이름 = 'Jack'을 쓰면 왜 오류가 날까?
WHERE는 SELECT보다 먼저 처리되어, 그 시점에는 별칭 이름이 아직 없기 때문입니다. ORDER BY 이름은 SELECT 다음에 처리되므로 별칭을 쓸 수 있어요.
보호 시작일이 똑같은 동물이 둘이면 정답 풀이는 누구를 돌려줄까?
둘 중 어느 쪽인지 정해져 있지 않습니다. 정렬 기준이 같은 행끼리의 순서는 보장되지 않아요. 항상 같은 결과가 필요하면 ORDER BY DATETIME, ANIMAL_ID처럼 두 번째 기준을 더합니다.

💼 이 유형을 다시 만나면"최신 글 10개", "가장 비싼 상품 3개"처럼 정렬 + LIMIT은 실무 쿼리에서 가장 많이 쓰는 모양이고, 게시판 페이지 나누기(LIMIT 10 OFFSET 20)도 같은 원리입니다. 같은 값이 있을 때 결과가 흔들리지 않도록 마지막 정렬 기준에 고유한 컬럼(ID)을 넣는 습관을 들이세요.

BOOK(책 ID·카테고리)과 BOOK_SALES(책 ID·판매일·판매량)에서 2022년 1월의 카테고리별 도서 판매량 합계를 CATEGORY, TOTAL_SALES로 조회하고 카테고리명 오름차순으로 정렬하는 문제. 원문 제목은 '도서 판매량 집계'로 줄여 적혀 있었다.

📄 제출 코드 파일 · 📁 22회차 전체 기록

SQL 제출 코드 · 오답노트 원문 (PASS) 
SELECT B.CATEGORY, SUM(S.SALES) AS TOTAL_SALES          -- ← 권수 합계 (건수 아님)
FROM BOOK B JOIN BOOK_SALES S ON B.BOOK_ID = S.BOOK_ID   -- ← 카테고리는 BOOK 쪽에
where YEAR(S.SALES_DATE) = '2022' AND MONTH(S.SALES_DATE) = '01'   -- ← 묶기 전에 1월만
GROUP BY B.CATEGORY
ORDER BY B.CATEGORY ASC;
💡 정답 풀이

제출 코드가 정답이다. 오답노트의 해설을 정리하면 이렇다. 1. JOIN — 카테고리는 BOOK에, 판매량은 BOOK_SALES에 있으니 BOOK_ID로 잇는다. 2. WHERE로 2022년 1월만 — YEAR(…) = '2022' AND MONTH(…) = '01'. MONTH()는 숫자 1을 돌려주지만, MySQL은 문자열 '01'과 숫자를 비교할 때 문자열을 숫자로 바꿔 같다고 본다. 그래서 = 1로 써도, = '01'로 써도 결과가 같다. 3. GROUP BY + SUM — 카테고리별로 묶고 SUM(S.SALES)로 권수를 더해 TOTAL_SALES라는 별칭을 붙인다. 4. ORDER BY — 카테고리명 오름차순.

실행 결과1월·2월·2021년 판매가 섞인 데이터로 먼저 예측 → 펼쳐서 확인 
제출 코드                                  → 경제|5, 생활|1, 인문|5
COUNT(*) 로 바꾸면 (판매 '건수')           → 경제|2, 생활|1, 인문|2
LIKE '2022-01%' 로                          → 경제|5, 생활|1, 인문|5

📌 주요 개념 정리

(1) COUNT vs SUM COUNT(*)는 행의 개수(판매 기록이 몇 건인가), SUM(컬럼)은 값의 합계(몇 권 팔렸나). 문제가 "판매량"을 물으면 SUM이다. → 🗄️ 17. 집계 함수 (2) 날짜로 거르는 세 가지 방법 ① 날짜 함수 YEAR(d) = 2022 AND MONTH(d) = 1 — 읽기 쉽다. ② 문자열 DATE_FORMAT(d, '%Y-%m') = '2022-01' 또는 d LIKE '2022-01%'. ③ 범위 d >= '2022-01-01' AND d < '2022-02-01' — 컬럼을 함수로 감싸지 않아 인덱스를 쓸 수 있는 형태라 데이터가 많을 때 가장 빠르다. 끝을 < '2022-02-01'로 잡으면 1월 31일 밤 시각까지 빠짐없이 들어간다. → 🗄️ 27. 날짜 함수 (3) WHERE가 GROUP BY보다 먼저 처리 순서상 WHERE로 1월 판매만 먼저 남긴 뒤 묶는다. 묶은 결과를 거를 때(예: 합계가 5 이상인 카테고리)만 HAVING을 쓴다. → 🗄️ 18. 🤔 스스로 확인

답을 펼치기 전에 머릿속으로 먼저 대답해 보세요. 오답노트는 다시 떠올려 봐야 내 것이 됩니다.

SUM(S.SALES)를 COUNT(*)로 바꾸면 결과는 무엇을 뜻하게 될까?
카테고리별 판매 기록의 건수가 됩니다. 한 기록에 3권이 팔렸어도 1로 세요. 위 실행 결과에서 경제가 5(권)에서 2(건)로 바뀐 이유입니다.
"1월 판매량 합계가 5권 이상인 카테고리만" 보여 주려면 조건을 어디에 써야 할까?
GROUP BY 뒤에 HAVING SUM(S.SALES) >= 5를 씁니다. 합계는 묶은 다음에야 나오므로 WHERE에는 쓸 수 없어요. 1월만 남기는 조건은 그대로 WHERE에 둡니다.
판매 기록이 수백만 건일 때 YEAR()·MONTH() 조건보다 범위 비교가 빠를 수 있는 이유는?
YEAR(SALES_DATE)처럼 컬럼을 함수로 감싸면 DB가 SALES_DATE 인덱스를 그대로 쓸 수 없어 모든 행에 함수를 계산해야 합니다. SALES_DATE >= '2022-01-01' AND SALES_DATE < '2022-02-01'은 컬럼을 그대로 두므로 인덱스로 해당 범위만 바로 찾을 수 있어요.

💼 이 유형을 다시 만나면"기간 + 그룹별 합계"는 매출 리포트·월별 통계처럼 실무에서 가장 많이 짜는 쿼리입니다. 기간 조건은 범위 비교로, 건수인지 합계인지는 문제(요구사항)의 단어로 판단하세요. 코딩테스트에서는 JOIN → WHERE → GROUP BY → ORDER BY 순서로 한 줄씩 붙여 가며 중간 결과를 확인하면 실수가 줄어듭니다.
