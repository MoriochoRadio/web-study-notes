없는 숫자 더하기

JAVA전체 합 − 있는 것의 합등차수열 합향상된 for · -=

한 줄 요약0~9의 합은 45로 정해져 있고 배열 원소는 모두 다르니, 45에서 배열에 있는 숫자를 모두 빼면 없는 숫자들의 합이 남는다. 무엇이 없는지 하나하나 찾을 필요가 없다.

쉽게 말하면0번부터 9번까지 공이 든 상자에서 몇 개를 꺼냈어요. 상자에 남은 공의 번호 합을 알려면 남은 공을 다 볼 필요 없이 "원래 합 45 − 꺼낸 공의 번호 합"이면 됩니다.

0부터 9까지의 숫자 중 일부가 들어 있는 정수 배열 numbers(길이 1~9, 원소는 모두 다름)가 주어질 때, 배열에 없는 0~9 숫자를 모두 찾아 더한 수를 반환하는 문제. [1,2,3,4,6,7,8,0] → 5 + 9 = 14.

📄 제출 코드 파일 · 📁 26회차 전체 기록

JAVA 제출 코드 · 오답노트 원문 (PASS) 
class Solution {
    public int solution(int[] numbers) {
        int sum = 45;                         // ← 0+1+…+9

        for(int i=0;i<numbers.length;i++){
            sum= sum-numbers[i];              // ← 있는 숫자를 하나씩 뺀다
        }

        return sum;                           // ← 남은 것 = 없는 숫자들의 합
    }
}
💡 정답 풀이

제출 코드가 정답이다. 원문에는 같은 생각을 for (int num : numbers) sum -= num;으로 다듬은 코드와 해설이 함께 적혀 있다. 왜 되나 — 여집합 0~9 전체 = 배열에 있는 것 + 없는 것. 원소가 모두 다르다는 조건 덕분에 "있는 것의 합"이 겹치지 않아, 전체 합에서 빼면 정확히 "없는 것의 합"이다. 흔히 틀리는 곳 1. 조건을 확인하지 않음 — 중복이 있으면 이 풀이는 깨진다. 조건 밖이지만 [9,9]를 넣으면 27(실제 없는 0~8의 합은 36). 문제의 "모두 다르다" 한 줄이 이 풀이의 전제다. 2. 하나하나 찾기 — 0~9마다 배열을 다 훑으면 이중 반복문이 된다. 여기서는 크기가 작아 상관없지만, 같은 문제를 1~n으로 키우면 차이가 커진다.

실행 결과가능한 입력 전부 먼저 예측 → 펼쳐서 확인 
공식 예제 [1,2,3,4,6,7,8,0] → 14 · [5,8,4,0,6,7,9] → 6          → 통과
0~9 의 부분집합 중 길이 1~9 인 것 전부 1,022개   → '없는 숫자를 직접 더한 값'과 모두 같음
(조건 밖) 중복 [9,9]                               → 27  (실제 36 — 중복이 없어야 되는 풀이)
원소가 모두 다르고 0~9 안이니, 가능한 배열은 0~9의 부분집합(순서만 다름)이에요. 그래서 1,022개(2^10 − 빈 것 − 전체)를 모두 돌려 볼 수 있었습니다. 로컬 검증이며 프로그래머스 재채점은 아닙니다.
📌 주요 개념 정리

(1) 여집합 — 전체에서 빼기 범위가 정해져 있고 중복이 없으며 구하는 것이 "합 · 개수"일 때, 하나하나 찾는 대신 전체 값에서 있는 것을 뺀다. 확인용 배열(boolean[])이 필요 없어진다. (2) 1부터 n까지의 합 = n(n+1)/2 0~9는 9×10/2 = 45. 범위가 커지면 상수 대신 공식으로. int를 넘을 수 있으면 long. → 내적(합의 범위 미리 계산) (3) 향상된 for문과 복합 대입 인덱스가 필요 없는 전체 순회는 for (int num : numbers), sum = sum - x는 sum -= x. → ☕ 9. 반복문 · ☕ 7. 연산자

n * (n + 1) / 2 - (배열의 합)이에요. 같은 여집합 생각입니다. n이 크면 곱이 int를 넘을 수 있으니 long으로 계산해요(또는 XOR로 찾는 방법도 있음).
중복이 있을 수 있는 문제로 바뀌면 어떻게 풀까?
boolean[] seen = new boolean[10]에 있는 숫자를 표시하고, 0~9 중 표시 안 된 것만 더해요. 전체 합에서 빼는 지름길은 "중복 없음"이라는 조건이 있을 때만 씁니다.

💼 이 유형을 다시 만나면"빠진 번호 찾기"(누락된 주문 번호, 비어 있는 좌석)는 실무에서도 자주 나와요. 범위와 중복 여부를 먼저 확인하고, 조건이 맞으면 합 · 개수로 한 번에, 아니면 Set으로 표시하는 두 갈래를 기억하세요.

타겟 넘버

JAVADFS · 재귀완전 탐색 2^n상태(index · sum)필드 초기화 주의

한 줄 요약숫자마다 더하기 / 빼기 두 갈래가 있으니 모든 경우는 2n가지(최대 220 ≈ 100만). 재귀 함수 dfs(index, sum)가 "지금 몇 번째 숫자인지"와 "지금까지의 합"을 들고 두 갈래로 내려가다, 끝(index == n)에서 합이 target이면 하나를 센다.

쉽게 말하면갈림길마다 왼쪽(+) · 오른쪽(−)이 있는 미로를 끝까지 다 걸어 보고, 도착한 곳의 점수가 목표와 같은 길이 몇 개인지 세는 거예요. 갈림길이 20개여도 길은 100만 개라 컴퓨터는 금방 다 걷습니다.

🔗 프로그래머스에서 문제 보기

음이 아닌 정수 배열 numbers(2~20개, 각 1~50)의 순서를 바꾸지 않고 각 수에 + 또는 -를 붙여 타겟 넘버(1~1000)를 만드는 방법의 수를 반환하는 문제. [1,1,1,1,1] · 3 → 5.

📄 제출 코드 칸의 코드 · 📁 26회차 전체 기록

JAVA 오답노트 제출 코드 칸 (원문 결과 FAIL) 
class Solution {
    int answer = 0;                                   // ← 정답 개수 (필드)

    public int solution(int[] numbers, int target) {
        dfs(numbers, target, 0, 0);                   // ← 0번 숫자부터, 합 0으로 시작
        return answer;
    }

    public void dfs(int[] numbers, int target, int index, int sum) {
        if (index == numbers.length) {                // ← 끝까지 왔으면
            if (sum == target) answer = answer + 1;   //    목표와 같을 때만 센다
            return;
        }
        dfs(numbers, target, index + 1, sum + numbers[index]);   // ← 더하는 길
        dfs(numbers, target, index + 1, sum - numbers[index]);   // ← 빼는 길
    }
}
💡 정답 풀이

원문 결과는 FAIL이지만, 제출 코드 칸에 적힌 이 코드는 로컬 검증에서 정답과 같은 값을 낸다. 시험 시간 안에 낸 코드인지는 기록만으로 알 수 없어 실패 원인은 단정하지 않았다. 원문 정답 풀이는 이 코드의 흐름(시작 · 분기 · 종료 판정)을 설명한다. 풀이의 세 단계 1. 시작 — dfs(numbers, target, 0, 0): 0번째 숫자, 합 0. 2. 분기 — index + 1로 다음 숫자로 가며 sum + numbers[index](더하기 길)와 sum - numbers[index](빼기 길) 두 번 호출. 3. 종료 · 판정 — index == numbers.length면 멈추고 sum == target일 때만 센다. 흔히 틀리는 곳 1. 상태를 직접 바꾸기 — sum += numbers[index]; dfs(…, sum) 다음 줄에서 빼기 길을 부르면 이미 더해진 sum에서 빼게 된다. 새 값을 인자로 넘겨야 갈림길마다 원래 상태가 남는다(원문 개념 3). 2. 종료 조건을 index == n - 1로 — 마지막 숫자를 반영하기 전에 멈춰 답이 틀린다. 3. 필드 answer를 0으로 되돌리지 않음 — 같은 객체로 solution을 두 번 부르면 5 → 10처럼 앞의 개수가 쌓인다(로컬에서 확인). solution 첫 줄에서 answer = 0;을 하거나, dfs가 개수를 return하게 만들면 안전하다.

실행 결과2^n 가지를 비트로 모두 세어 본 값과 비교 먼저 예측 → 펼쳐서 확인 
공식 예제 [1,1,1,1,1]/3 → 5 · [4,1,2,1]/4 → 2                 → 통과
무작위 2,000개 (숫자 2~14개, 1~50)                              → 비트로 2^n 가지를 모두 센 값과 같음
최대 크기: 숫자 20개(모두 1) · 목표 2                            → 167,960가지, 이 PC에서 2.6ms (2^20 = 1,048,576 갈래)
같은 객체로 두 번 호출 [1,1,1,1,1]/3                            → 5 → 10  (answer 필드가 남아 있음)
기댓값은 재귀를 쓰지 않는 별도 코드예요 — mask의 i번째 비트가 1이면 +, 0이면 −로 2n개를 모두 만들어 셉니다(시드 26 고정). 167,960은 20개 중 +가 11개 · −가 9개인 경우의 수 C(20, 9)와 같아 결과가 맞는지도 손으로 확인돼요. 로컬 검증이며 프로그래머스 재채점은 아닙니다.
📌 주요 개념 정리

(1) DFS와 완전 탐색 모든 경우를 빠짐없이 보는 방법. 갈래가 2개씩 n단계면 2n. n ≤ 20이면 약 100만이라 충분히 빠르다(문제 크기를 보고 완전 탐색이 되는지 먼저 계산). (2) 상태 공간 트리 — 무엇을 들고 다니나 index(지금 몇 번째)와 sum(지금까지 합) 두 가지. 재귀 호출의 인자가 곧 상태다. (3) 재귀의 매개변수 전달 — 덮어쓰지 말고 넘긴다 dfs(index + 1, sum + x)처럼 계산한 값을 넘기면 돌아왔을 때 내 sum은 그대로라, 다음 갈래(sum - x)를 바로 시작할 수 있다(백트래킹). → 기능개발(큐) · 올바른 괄호(스택)

대장균의 크기에 따라 분류하기 2

SQL윈도우 함수NTILE · PERCENT_RANK · CUME_DISTOVER (ORDER BY)경계 <=

한 줄 요약크기 내림차순으로 줄 세웠을 때 상위 25%씩 네 묶음으로 나눠 CRITICAL · HIGH · MEDIUM · LOW를 붙인다. 개별 행을 지운 채 묶는 GROUP BY로는 "전체 중 몇 번째"를 알 수 없어서, 행을 그대로 두고 순위 · 비율을 옆에 붙여 주는 윈도우 함수(NTILE(4) · PERCENT_RANK() · CUME_DIST())를 쓴다.

쉽게 말하면반 학생을 키 큰 순서로 줄 세운 뒤 앞에서부터 4분의 1씩 끊어 1조 · 2조 · 3조 · 4조를 정하는 거예요. NTILE은 조 번호를 바로 붙여 주고, PERCENT_RANK · CUME_DIST는 "앞에서 몇 % 지점"을 알려 줘서 그걸로 끊습니다.

🔗 프로그래머스에서 문제 보기

대장균 개체 테이블 ECOLI_DATA에서 크기(SIZE_OF_COLONY)를 내림차순으로 정렬했을 때 상위 0~25%는 CRITICAL, 26~50%는 HIGH, 51~75%는 MEDIUM, 76~100%는 LOW로 분류해 ID와 COLONY_NAME을 ID 오름차순으로 출력하는 문제. 전체 데이터 수는 4의 배수이고, 같은 크기의 개체가 서로 다른 이름으로 분류되는 경우는 없다.

📄 정답 풀이 1 (NTILE) · 📄 풀이 2 (PERCENT_RANK) · 📄 풀이 3 (CUME_DIST) · 📁 26회차 전체 기록

SQL 정답 풀이 1 · 2 (오답노트 원문) · 제출 코드 칸은 비어 있음 
-- 풀이 1: NTILE(4) — 4묶음 번호를 바로
SELECT ID,
       CASE NTILE(4) OVER (ORDER BY SIZE_OF_COLONY DESC)   -- ← 큰 것부터 1 · 2 · 3 · 4
           WHEN 1 THEN 'CRITICAL'
           WHEN 2 THEN 'HIGH'
           WHEN 3 THEN 'MEDIUM'
           ELSE 'LOW'
       END AS COLONY_NAME
FROM ECOLI_DATA
ORDER BY ID ASC;                                           -- ← 최종 정렬은 따로

-- 풀이 2: PERCENT_RANK — 0(맨 앞) ~ 1(맨 뒤) 비율로 끊기
SELECT ID,
       CASE WHEN PR <= 0.25 THEN 'CRITICAL'
            WHEN PR <= 0.50 THEN 'HIGH'
            WHEN PR <= 0.75 THEN 'MEDIUM'
            ELSE 'LOW' END AS COLONY_NAME
FROM (SELECT ID, PERCENT_RANK() OVER (ORDER BY SIZE_OF_COLONY DESC) AS PR
      FROM ECOLI_DATA) AS SUB
ORDER BY ID ASC;
💡 정답 풀이

제출 코드 칸이 비어 있어 실패 원인은 단정하지 않았다. 원문에는 세 가지 정답 풀이(NTILE · PERCENT_RANK · CUME_DIST)와 해설이 적혀 있다. 풀이의 세 단계 1. 순위 붙이기 — 윈도우함수() OVER (ORDER BY SIZE_OF_COLONY DESC): 행을 줄이지 않고 큰 것부터의 위치를 옆에 붙인다. 전체를 한 줄로 보니 PARTITION BY는 없다. 2. 이름 붙이기 — CASE로 번호(1~4)나 비율(≤ 0.25 · ≤ 0.50 · ≤ 0.75)을 이름으로. 3. 최종 정렬 — OVER 안의 정렬은 순위용일 뿐이라, 결과 순서는 바깥 ORDER BY ID로 따로 정한다. 세 함수가 같은 답을 내는 이유 개체가 4k개이고 크기가 겹치지 않으면, 앞에서 p번째(0부터)의 PERCENT_RANK = p / (4k−1), CUME_DIST = (p+1) / 4k. 경계(0.25 · 0.50 · 0.75)를 <=로 끊으면 두 값 모두 정확히 k개씩 나뉜다(개체 4 · 8 · 12 · 20개로 세 풀이를 돌려 모두 같은 답을 확인). 흔히 틀리는 곳 1. DESC 빠뜨림 — 작은 것이 CRITICAL이 된다. 2. CUME_DIST를 <로 — 8개일 때 두 번째 개체가 정확히 0.25라 CRITICAL에서 빠진다(2개가 아니라 1개). 3. 바깥 ORDER BY ID 빠뜨림 — 창 함수의 정렬 순서로 나올 수 있다.

📌 주요 개념 정리

(1) 윈도우 함수 — 행을 지우지 않고 옆에 값 함수() OVER (PARTITION BY 그룹 ORDER BY 기준). GROUP BY는 묶어서 한 줄로 줄이지만, 창 함수는 행을 그대로 두고 순위 · 비율 · 누적을 붙인다. 결과를 거르려면 서브쿼리로 감싼다. → 일정관리의 ROW_NUMBER(날마다 3개) (2) NTILE · PERCENT_RANK · CUME_DIST NTILE(N): 1~N 묶음 번호(남는 행은 앞 묶음부터 하나씩). PERCENT_RANK(): (순위−1)/(전체−1), 0~1. CUME_DIST(): 나보다 앞서거나 같은 행의 비율, 0 초과~1. (3) 순위 함수 가족 ROW_NUMBER(같아도 1 · 2 · 3) · RANK(같으면 같은 번호, 다음은 건너뜀) · DENSE_RANK(건너뛰지 않음). → 대장균 분류 1(CASE 구간)

답을 펼치기 전에 머릿속으로 먼저 대답해 보세요. 오답노트는 다시 떠올려 봐야 내 것이 됩니다.

"부모 개체(PARENT_ID)별로 크기 순위 1등만" 고르려면 어디를 바꿀까?
ROW_NUMBER() OVER (PARTITION BY PARENT_ID ORDER BY SIZE_OF_COLONY DESC) AS RN을 서브쿼리에서 붙이고 바깥에서 WHERE RN = 1. 오늘 일정관리의 "날마다 3개"와 같은 틀이에요(실행하지 않은 쿼리).
NTILE 풀이에서 바깥 ORDER BY ID 를 빼도 결과가 맞을까?
값(이름)은 맞지만 순서가 보장되지 않아요. 창 함수를 계산하느라 크기 순으로 나올 수도 있고, 채점은 ID 오름차순을 요구하니 오답이 될 수 있습니다. SQL은 ORDER BY를 쓰지 않으면 순서를 약속하지 않아요.

💼 이 유형을 다시 만나면"상위 n%", "등급 매기기", "그룹별 상위 n개", "누적 합"은 윈도우 함수 영역이에요 — 리포트 · 대시보드 쿼리의 핵심입니다. 오늘처럼 같은 문제를 세 가지 함수로 풀어 보면 각 함수의 정의(어디가 0이고 어디가 1인지)가 확실히 남아요.
