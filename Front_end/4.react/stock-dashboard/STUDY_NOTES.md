## 1. `useLiveTicker.js` — WebSocket + `useEffect` cleanup

**핵심 개념**: `useEffect`, cleanup 함수, `useRef`

**왜 cleanup이 필요한가**
`useEffect`는 컴포넌트가 리렌더링될 때마다 다시 실행될 수 있습니다(의존성 배열이
바뀌면). 이때 이전 `useEffect`가 만든 WebSocket 연결을 정리하지 않으면, 연결이
계속 쌓여서 같은 메시지를 여러 번 받거나 메모리를 낭비하게 됩니다. `return () =>
{...}`로 등록한 cleanup 함수는 "다음 effect가 실행되기 직전" 또는 "컴포넌트가
사라질 때" 자동으로 호출됩니다.

**예상 질문 1**: "`ws.close()`만 부르면 안 되나요? 왜 `unsubscribe` 메시지를 먼저
보내나요?"
→ `ws.close()`는 클라이언트 쪽 연결만 끊습니다. Finnhub 서버 입장에서는 아직 이
클라이언트가 특정 심볼을 구독 중이라고 인식하고 있을 수 있어서, 명시적으로
`unsubscribe` 메시지를 먼저 보내 서버 쪽 구독 상태도 정리해주는 게 더 안전합니다.

**예상 질문 2**: "의존성 배열에 `[symbols]`를 넣은 이유는?"
→ 구독할 종목 목록이 바뀔 때만 WebSocket을 새로 맺어야 하고, 컴포넌트가
리렌더링될 때마다(예: 다른 state가 바뀔 때) 매번 재연결하면 안 되기 때문입니다.
`symbols`가 실제로 바뀔 때만 이전 연결을 정리하고 새로 연결합니다.

**예상 질문 3**: "가격 방향(상승/하락)은 어떻게 저장하나요? `useState`로 하면 안
되나요?"
→ 이전 가격은 "비교용"으로만 쓰고 화면에 그 값 자체를 보여주는 게 아닙니다.
`useState`로 저장하면 값이 바뀔 때마다 불필요한 리렌더링이 발생하지만, `useRef`는
값을 기억하되 리렌더링을 유발하지 않아서 이런 "내부 비교용 값"에 적합합니다.

**한 문장 요약**: "연결을 여는 곳이 있으면 반드시 정리하는 곳도 있어야 한다"는
원칙을 `useEffect` cleanup으로 구현한 것.

## 2. `useWatchlistStore.js` — Zustand `create` + `persist`

**핵심 개념**: 전역 상태관리, `persist` 미들웨어, 불변성(immutability)

**왜 Context API가 아니라 Zustand인가**
Context API는 Provider로 트리를 감싸야 하고, 값이 바뀌면 그 Context를 구독하는
모든 하위 컴포넌트가 리렌더링될 수 있습니다. Zustand는 Provider 없이 훅 하나
(`useWatchlistStore()`)로 전역 상태에 접근하고, 필요한 값만 꺼내 쓸 수 있어
설정이 간단합니다.

**예상 질문 1**: "`addSymbol`에서 `watchlist.push(symbol)`처럼 바로 추가하면 안
되나요?"
→ `push`는 기존 배열을 그 자리에서 변형(mutate)합니다. React/Zustand는 "참조가
달라졌는지"로 변경을 감지하는데, `push`는 배열 참조 자체는 그대로라서 변경을
감지하지 못하고 화면이 갱신되지 않을 수 있습니다. 그래서 `[...state.watchlist,
symbol]`처럼 매번 새 배열을 만들어 반환합니다.

**예상 질문 2**: "`persist`는 내부적으로 어떻게 동작하나요?"
→ 상태가 바뀔 때마다 `persist` 미들웨어가 자동으로 상태를 JSON으로 직렬화해
`localStorage.setItem(name, ...)`을 호출합니다. 앱이 다시 로드될 때는
`localStorage`에서 값을 읽어 초기 상태로 복원합니다. `name: 'watchlist-storage'`가
그 저장 키입니다.

**예상 질문 3**: "`set`과 `get`의 차이가 뭔가요?"
→ `set`은 상태를 바꾸는 함수(리액트의 `setState`와 비슷), `get`은 현재 상태를
"읽기만" 하는 함수입니다. `isWatched`처럼 상태를 바꾸지 않고 조회만 할 때는
`get()`을 씁니다.

**한 문장 요약**: "여러 컴포넌트가 같은 데이터를 공유해야 하고, 새로고침해도
유지되어야 한다"는 요구사항을 Zustand의 `create`+`persist` 조합으로 해결한 것.

## 3. `search/route.js` (기능 1) — fetch → json 파싱, 3라운드 디버깅

**핵심 개념**: `fetch`, `Promise`/`async-await`, 서버 응답 구조 파악

**왜 `Response` 객체와 실제 데이터가 다른가**
`fetch()`가 즉시 반환하는 건 HTTP 응답의 메타정보(status, headers 등)를 감싼
`Response` 객체입니다. 실제 본문(body) 데이터를 꺼내려면 `.json()`이라는 별도의
"비동기" 메서드를 한 번 더 호출(`await`)해야 합니다. 이걸 몰라서 1차 시도에서는
`Response` 객체에 `.filter()`를 걸었다가 실패했습니다.

**예상 질문 1**: "Finnhub 응답이 배열이 아니라 `{ count, result }` 객체인 걸 어떻게
알았나요?"
→ 브라우저 개발자도구 Network 탭에서 실제 응답 body를 직접 확인했습니다. 문서만
보고 짐작하지 않고 실제로 호출해서 구조를 확인하는 게 중요하다는 걸 이때
배웠습니다.

**예상 질문 2**: "왜 클라이언트에서 다시 `q`로 필터링하지 않았나요?"
→ Finnhub 검색 API가 서버에서 이미 `q` 기준으로 필터링을 끝내고 결과를 줍니다.
클라이언트에서 `symbol`/`name`에 `q`가 포함되는지 다시 검사하면, Finnhub가
별칭·유사 종목 로직으로 매칭시킨 결과를 우리의 단순 문자열 검사가 오히려 걸러낼
위험이 있어서, 필드명만 맞춰주는 `.map()`으로 바꿨습니다.

**한 문장 요약**: "AI에게 정답을 바로 받지 않고 매번 '왜 안 되는지'만 물어서
직접 고쳤다"는 과정 자체가 이 사례의 핵심 — 코드 내용뿐 아니라 디버깅 방식도
질문받을 수 있는 부분입니다.

## 4. Hooks 규칙 위반 (`StockQuoteCard`, 기능 8)

**핵심 개념**: React Hooks 규칙(호출 순서 고정)

**왜 조건부 `return` 뒤에 훅을 두면 안 되는가**
React는 훅을 "몇 번째로 호출됐는지" 순번으로 내부 상태를 관리합니다. 첫 렌더링에서
5개 훅이 호출됐는데, 다음 렌더링에서 조건(`if (!symbol) return null` 등) 때문에
3개만 호출되면, React는 4번째·5번째 훅이 이전 렌더링의 어떤 훅과 대응하는지
매칭할 수 없습니다. 그 결과 상태가 뒤섞이거나 런타임 에러가 날 수 있습니다.

**예상 질문**: "그럼 왜 `isWatched(data.symbol)`은 조건부 `return` 뒤에 있어도
괜찮나요?"
→ `isWatched`는 훅이 아니라 스토어에서 이미 꺼내온 "일반 함수"입니다. Hooks
규칙은 훅 호출 자체(`useState`, `useEffect`, `useWatchlistStore()` 같은 것)에
적용되는 것이지, 훅에서 꺼낸 값이나 함수를 나중에 쓰는 것과는 무관합니다. 이
차이를 구분하는 게 핵심입니다.

**한 문장 요약**: "훅을 호출하는 것"과 "훅에서 꺼낸 값을 쓰는 것"은 다른
문제라는 걸 이 버그를 통해 배웠다.

## 5. 해외 종목(D.BK) 응답 검증 누락 (기능 2)

**핵심 개념**: 외부 API 신뢰 경계, 서버 사이드 유효성 검증

**예상 질문**: "200 응답이면 안전한 거 아닌가요?"
→ HTTP 200은 "요청이 성공적으로 처리됐다"는 뜻이지, "우리가 기대하는 형태의
데이터가 들어있다"는 보장은 아닙니다. Finnhub 무료 플랜이 D.BK 같은 특정 종목의
실시간 시세를 지원하지 않으면, 200을 주면서도 `data.c`(현재가) 필드 자체가 없는
응답을 줄 수 있습니다. 그래서 서버(`route.js`)에서 `typeof data.c !== 'number'`로
값을 직접 검증하고, 실패 시 명확한 에러 상태 코드(404)로 바꿔줬습니다.

**한 문장 요약**: "외부 API는 성공 응답이어도 데이터 형태를 보장하지 않는다"는
걸 실제 버그로 체감한 사례.

## 6. `recommendation/route.js` 오사용 (최종 통합 테스트)

**핵심 개념**: 정적 코드 리뷰의 한계, 통합 테스트의 필요성

**예상 질문**: "왜 문법 에러도 안 났는데 발견이 늦었나요?"
→ `recommendation/route.js`와 `earnings/route.js`가 구조(fetch → 검증 → 반환)가
거의 똑같아서, 파일 내용을 통째로 헷갈려 저장해도 둘 다 문법적으로는 완전히
정상인 JS 코드였습니다. 컴포넌트도 배열을 객체처럼 다루려다 보니
(`rec.symbol`, `rec.buy` 등이 전부 `undefined`) 에러 없이 조용히 빈 화면만
나와서 코드만 읽는 리뷰로는 잡을 수 없었고, 실제로 브라우저에서 값을 찍어봐야만
발견할 수 있었습니다.

**한 문장 요약**: "코드가 문법적으로 맞다고 해서 옳은 건 아니다" — 최종 통합
테스트가 왜 필요한지 보여주는 사례.
