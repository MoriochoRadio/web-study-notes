# 📝 AI 프롬프트 일지 (PROMPT_LOG.md)

AI에게 어떤 지시를 내렸고, 원하는 결과를 얻기 위해 프롬프트를 어떻게 발전시켰는지
기록합니다. 기능마다 진행 방식은 거의 비슷했습니다. 참고할 기존 강의 파일을 먼저
정하고, API 응답 형식처럼 제가 모르는 부분만 물어본 다음 코드는 직접 작성하고,
"이렇게 했는데 리뷰해줘"라고 요청해서 지적받은 원인을 보고 수정했습니다.

## 1) 프롬프트 작성 이력 (최소 3개)

### 프롬프트 1 — 프로젝트 스캐폴딩
**참고한 강의 파일**: `lessons/07~13` 전체. 이후 기능마다 강의에서 쓰던 패턴을 그대로
가져다 쓸 생각이었기 때문에, 시작부터 버전을 강의와 맞춰둬야 했습니다.

**프롬프트 전문**: "4.react/stock-dashboard 자리에 create-next-app으로 JS + Tailwind v4 +
App Router + ESLint 조합으로 새 프로젝트를 만들어줘. 기존 lessons/07~13 강의와 같은
Next / React 버전, zustand·recharts 추가 설치."

**AI 답변 요약**: 지정한 옵션 그대로 `create-next-app`을 실행하는 명령과
`zustand`/`recharts` 설치 명령을 제시했습니다. 기본 Geist 폰트/템플릿이 포함되니
13강 `globals.css`의 색상 팔레트를 재사용하려면 직접 교체해야 한다는 점도 함께
안내했습니다.

**적용한 방식**: 안내받은 대로 기본 템플릿을 지우고 13강 팔레트와 다크모드 설정을
옮겨왔습니다. 빌드가 정상적으로 도는 것도 확인했습니다.

### 프롬프트 2 — 기능 1: 스마트 주식 검색 (`api/search/route.js`)
**참고한 강의 파일**: `lessons/09`의 로컬 배열 검색용 `route.js`

**바꿔야 했던 부분**: 09강 코드는 서버에 이미 있는 로컬 배열을 `.filter()`로 걸러서
돌려주는 구조였습니다. 저는 로컬 데이터가 아니라 Finnhub API를 매번 호출해서 그
결과를 검색 결과로 써야 했어서, "가진 데이터를 거르는 로직"을 "매번 새로 요청해서
받아온 데이터를 우리 형식에 맞게 가공하는 로직"으로 바꿔야 했습니다. 09강 골격을
어디까지 그대로 쓰고 어디부터 새로 짜야 하는지 감이 안 와서 물어봤습니다.

**프롬프트 전문**: "09강 lessons/09의 로컬 검색용 route.js 구조를 참고해서 Finnhub
API를 쓸 건데, API 키는 `process.env.FINNHUB_API_KEY`로 서버에서만 읽고 클라이언트에는
노출하면 안 돼. 응답이 실제로 어떤 필드명(symbol, name 등)으로 오는지 예시 JSON만
보여줘."

**AI 답변 요약**: Finnhub `/v1/search` 응답이 `{ count, result: [...] }` 형태이고,
배열 안 각 항목은 `symbol`이 아니라 `displaySymbol`/`description`/`type` 필드로
온다는 예시 JSON을 알려줬습니다. API 키를 서버 전용 환경변수(`FINNHUB_API_KEY`,
`NEXT_PUBLIC_` 접두사 없음)로 유지해야 클라이언트 번들에 노출되지 않는다는 점도
짚어줬습니다.

**적용한 방식**: 09강의 "요청 파싱 → 결과 가공 → 응답" 골격은 그대로 가져오고,
데이터 소스만 로컬 배열에서 `fetch` 결과로 바꿨습니다. Finnhub 필드명을 프로젝트에서
쓰는 이름으로 매핑하는 부분은 새로 짰습니다. 이렇게 만든 `route.js`를 실제로
돌리다가 겪은 3라운드 디버깅 과정은 아래 "2) 프롬프트 재작성 경험"에 정리했습니다.

### 프롬프트 3 — 기능 3: WebSocket 실시간 체결가 전광판 (`useLiveTicker.js`)
**참고한 강의 파일**: 13강 `StockChart.jsx`의 단일 종목 WebSocket 구독 패턴

**바꿔야 했던 부분**: 13강 코드는 종목 하나만 WebSocket으로 구독하는 구조였습니다.
저는 AAPL/TSLA/NVDA 세 종목을 하나의 연결로 동시에 구독해야 했어서, "구독 메시지
하나 보내기"를 "여러 종목을 순회하며 구독/해제 메시지를 반복해서 보내기"로 넓혀야
했습니다.

**프롬프트 전문**: "13강 StockChart.jsx는 종목 하나만 WebSocket으로 구독하는데,
나는 AAPL/TSLA/NVDA 세 종목을 하나의 WebSocket 연결로 동시에 구독하고 싶어. Finnhub
WebSocket에서 여러 심볼을 한 연결에 구독/해제하는 메시지 형식이랑, useEffect
cleanup에서 연결을 어떻게 정리해야 하는지 알려줘."

**AI 답변 요약**: `{type: 'subscribe', symbol: '...'}` 메시지를 심볼마다 반복해서
보내면 한 연결로 여러 종목을 구독할 수 있고, `useEffect`의 cleanup에서는
`unsubscribe` 메시지를 먼저 보낸 뒤 `ws.close()`로 연결을 끊어야 서버 쪽 구독까지
정리된다는 점을 알려줬습니다. 이전 체결가와 비교해 상승/하락 방향을 표시하려면
리렌더링을 유발하지 않고 직전 값만 기억하는 `useRef`가 적합하다는 것도 이때
배웠습니다.

**적용한 방식**: 13강의 단일 구독 `useEffect` 구조는 그대로 두고, 구독/해제 메시지만
`symbols.forEach(...)`로 배열을 도는 형태로 넓혔습니다. 가격 변동 방향을 감지하는
`useRef` 로직은 직접 새로 짰습니다.

### 프롬프트 4 — 기능 8: 관심 종목 관리 (`useWatchlistStore.js`)
**참고한 강의 파일**: 12강(`12_tailwind_darkmode`)의 Zustand `create`+`persist`
다크모드 토글 패턴

**바꿔야 했던 부분**: 12강 코드는 다크모드 값 하나(`'dark' | 'light'`)만 전역으로
토글하는 스토어였습니다. 저는 이 패턴을 "종목 심볼 배열"이라는 완전히 다른 상태로
넓혀야 했고, 단일 값 토글 대신 배열 추가/삭제/조회 액션(`addSymbol`/
`removeSymbol`/`isWatched`)을 직접 설계해야 했습니다.

**프롬프트 전문**: "Zustand의 `create`랑 `persist`를 조합해서 관심 종목 배열을
전역 상태로 관리하고, 새로고침해도 `localStorage`에서 값이 복원되게 하고 싶어.
`create`/`persist` 구조랑 `set`/`get`의 차이를 설명해줘."

**AI 답변 요약**: `create(persist(상태정의함수, 저장옵션))` 구조에서 `persist`는
상태가 바뀔 때마다 `localStorage`에 자동 저장하는 역할을 하고, `set`은 상태를 바꾸는
함수, `get`은 현재 상태를 읽는 함수(리액트의 `setState`/현재 state 접근과 비슷한
역할)라는 설명을 받았습니다. 배열에 새 값을 추가할 때 원본을 직접
수정(`push`)하면 변경 감지가 안 되니 `[...기존배열, 새값]`처럼 새 배열을 만들어
반환해야 한다는 점도 안내받았습니다.

**적용한 방식**: 12강의 `create(persist(...))` 골격은 그대로 가져오고, 다크모드
단일 값 토글 로직 대신 종목 배열을 다루는 `watchlist`/`addSymbol`/`removeSymbol`/
`isWatched`를 직접 설계해서 작성했습니다.

기능 2(실시간 시세), 4(차트), 5(투자의견), 6(어닝), 7(뉴스 피드)도 같은 방식으로
진행했습니다 — 기존 강의 파일의 구조를 가져와서 필요한 부분만 응용해 넓히고,
모르는 개념만 질문한 뒤 직접 작성하고 리뷰를 요청했습니다.

## 2) 프롬프트 재작성(Iterative Prompting) 경험 (최소 1개)

### 사례 A — 기능 1 백엔드: 3라운드에 걸친 재질문
1차 시도를 리뷰받았을 때는 "`symbol`과 `apiKey`라는 변수를 선언한 적이 없는데
참조하고 있다"는 지적을 받아 `ReferenceError`를 고쳤습니다. 재질문해서 원인만 다시
들은 2차 시도는 `fetch()`가 돌려주는 `Response` 객체에는 `.filter()` 메서드가
없다는 걸 놓쳐 여전히 실패했습니다. "그러면 `Response`에서 실제 데이터는 어떻게
꺼내야 해?"라고 다시 물어봐서 `await res.json()`이 필요하다는 답을 들었고, 3차
시도에서야 `data.result`가 진짜 배열이고 실제 필드명이 `displaySymbol`/
`description`이라는 것까지 확인해 제대로 고쳤습니다. 매 라운드 정답 코드를 바로
받지 않고 "왜 안 되는지"만 물어서 스스로 고쳤습니다. Before/After 코드는
[`CODE_REVIEW.md`](./CODE_REVIEW.md) 사례 1에 있습니다.

### 사례 B — 기능 8: Hooks 규칙 위반 재질문
`useWatchlistStore()`를 조건부 `return` 네 개보다 뒤에서 호출해뒀는데 화면이
이상하게 동작해서 "이 코드 왜 이런 거야?"라고 리뷰를 요청했습니다. React Hooks
규칙(훅은 매 렌더링마다 항상 같은 순서로 호출돼야 함) 위반이라는 지적을 받고, 훅
호출을 컴포넌트 최상단으로 옮겼습니다. 이어서 "그럼 훅에서 꺼낸 값을 조건부
return 뒤에서 쓰는 것도 안 되는 거야?"라고 다시 물어봐서, 훅 호출 자체와 훅에서
꺼낸 일반 값/함수의 사용은 다른 문제라는 걸 확인했습니다. Before/After 코드는
[`CODE_REVIEW.md`](./CODE_REVIEW.md) 사례 5에 있습니다.
