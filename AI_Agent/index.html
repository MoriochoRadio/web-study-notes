3. 계속 다시 나올 큰 생각

  • 짧게 쓰는 대신 규칙을 정확히 — 파이썬은 타입 선언이 없어 실수가 실행할 때 드러나요. type()으로 확인하고, 들여쓰기 · 끝 미포함(range · 슬라이싱)을 몸에 익혀요.
  • "한 줄로"는 읽을 수 있을 때만 — 삼항 표현식 · 리스트 컴프리헨션 · lambda는 편하지만, 조건이 길어지면 보통 for · if · def가 더 읽기 쉬워요.
  • 원본이 바뀌는가, 새것을 돌려주는가 — strip() · sorted() · rename() · fillna() · drop()은 새것을 돌려줘서 다시 담아야 하고, list.sort() · append() · df["새열"] = …는 그 자리에서 바뀌어요. Day 1(점수 분석)과 Day 3(정제)에서 같은 실수가 다른 모양으로 나왔어요.
  • 노트북은 위에서 아래로 다시 실행해 본다 — 칸을 고치고 다시 안 돌리면 출력이 옛것으로 남고(Day 2 구구단 · Day 3 종합), 앞 칸이 바꾼 변수 때문에 예제 칸이 KeyError가 나요(Day 3). 제출 · 공유 전에는 "모두 다시 실행".
  • 환경을 프로젝트마다 나눈다 — 가상환경(venv)은 자바의 Maven 의존성처럼 프로젝트마다 라이브러리 버전을 따로 둡니다. Day 7부터 LangChain 같은 큰 라이브러리가 들어오면 더 중요해져요.
  • 들어온 값은 믿지 않고 검사한다 — Day 5의 타입 힌트 · Pydantic은 형식이 틀린 요청을 함수에 닿기 전에 422로 돌려보내요. 백엔드 과정의 "브라우저에서 온 값은 믿지 않는다"(@Validated)와 같은 생각이고, 없는 자원처럼 뜻이 담긴 실패(404)는 여전히 내가 직접 정해요.
  • 비밀값은 코드 밖에 둔다 — Day 6의 API 키는 .env + load_dotenv(), Day 5 DB 비밀번호도 같은 방식이 맞아요. 이 저장소는 백엔드 과정 내내 수업 사본의 DB 비밀번호를 YOUR_DB_PASSWORD로 가려 왔고, 오늘 .env를 .gitignore에 넣었어요. 노출되면 지우는 게 아니라 바꾸는 것이 답이에요.
  • 밖과 주고받는 것은 형식을 정한다 — 파일은 encoding="utf-8"(엑셀용 CSV는 utf-8-sig), JSON은 force_ascii=False, 서버(Day 5)는 JSON, LLM(Day 7)은 프롬프트 형식. 백엔드 과정의 "JSON 키 · 상태 코드 약속"과 같은 생각이에요.
  • 같은 이름, 다른 계산 — 표준편차가 Pandas describe()는 13.70, np.std는 12.25(py-13). 숫자를 남에게 보여 줄 땐 어떤 정의로 계산했는지까지 확인해요.

① 서버 띄우기 — 함수 하나가 API 하나

app = FastAPI()를 만들고 함수 위에 @app.get("/")를 붙이면, 그 주소로 GET 요청이 올 때 함수가 불리고 돌려준 딕셔너리가 JSON 응답이 돼요. 실행은 uvicorn main:app --reload(main.py 파일의 app 변수), 브라우저 http://127.0.0.1:8000/docs에 Swagger 문서가 저절로 생겨 거기서 바로 시험해요. → py-16

② 값을 받는 세 자리 — 경로 · 쿼리 · 본문

주소 속 {number}와 같은 이름의 매개변수는 경로 파라미터, 그 밖의 매개변수는 쿼리 파라미터(기본값이 있으면 선택), BaseModel 타입 매개변수는 요청 본문(JSON). 타입 힌트(int · bool)에 맞지 않으면 함수가 불리기도 전에 422로 돌려보내요. → py-17 · py-18 · py-19

③ CRUD와 에러 — 메서드 넷과 404

@app.get 조회 · @app.post 생성 · @app.put 수정 · @app.delete 삭제, 없는 자원은 raise HTTPException(status_code=404, detail=…). 저장소는 아직 DB가 아니라 파이썬 리스트 · 딕셔너리(members_db · products_db)라 서버를 끄면 사라져요. → py-20

④ 서버를 띄워 요청을 보내 보니 — 짚을 곳

내 main.py에는 GET /products/{product_id}가 세 번(12쪽 1번 · 2번, 17쪽 1번) 등록돼 있어, 먼저 등록된 함수만 불려요 — show_tax가 무시되고, 없는 상품(/products/99)도 404가 아니라 200, PUT으로 고친 상품이 GET에 안 보여요. 서버도 실행 중 Duplicate Operation ID 경고를 냈어요(실습 27). 선생님은 종합 실습을 /products17/…로 옮겨 이 충돌을 피했어요.

PYTHONday05/main.py — 교안 5쪽 첫 서버 (그대로)
from fastapi import FastAPI

app = FastAPI(title="나만의 첫 API 서버")      # ← 서버(애플리케이션) 한 개

@app.get("/")                                   # ← GET /  요청이 오면
def read_root():
    return {"message": "Hello, FastAPI!"}       # ← 딕셔너리 → JSON 응답

@app.get("/hello/{name}")                       # ← {name} 자리의 글자가
def say_hello(name: str):                       #    같은 이름 매개변수로
    return {"message": f"{name}님, 안녕하세요!"}

# 터미널:  uvicorn main:app --reload   (안 되면 python -m uvicorn main:app --reload)
실행 결과저장소 밖 사본을 uvicorn으로 띄우고 요청 먼저 예측 → 펼쳐서 확인 
GET /              → 200 {"message":"Hello, FastAPI!"}
GET /hello/태경     → 200 {"message":"태경님, 안녕하세요!"}
GET /docs          → 200 Swagger UI 페이지
GET /square/abc    → 422 {"detail":[{"type":"int_parsing","loc":["path","number"], …}]}
FastAPI 0.156.4 · Pydantic 2.14.1 · uvicorn 0.54.0(이 PC의 파이썬 3.15에 설치된 것). 브라우저 대신 Node fetch로 요청을 보냈어요. 상태 줄의 422 이름은 이 버전에서 Unprocessable Content로 나와요(교안은 예전 이름 Unprocessable Entity — 같은 422).
3일차에 배운 것 — 핵심 정리
  • @app.메서드("경로") + 함수 = API 하나, 돌려준 딕셔너리 = JSON.
  • 실행 uvicorn main:app --reload, 시험은 /docs.
  • 경로에 있으면 Path, 없으면 Query(기본값 있으면 선택), BaseModel이면 Body.
  • 타입이 안 맞으면 422(자동), 없는 자원은 HTTPException(404)(직접).
  • 같은 메서드 + 같은 경로는 하나만 — 두 번 쓰면 먼저 등록된 것만 동작.

snake_case/ // % **== !=and or nottype()

한 줄 요약이름 = 값이면 변수가 생기고 타입은 값이 정한다. 나눗셈 /는 언제나 실수, 몫은 //, 나머지는 %, 거듭제곱은 **. 비교 결과는 True/False, 논리는 영어 단어 and · or · not.

쉽게 말하면자바처럼 "이 상자엔 정수만" 하고 상자 모양을 먼저 정하지 않아요. 상자에 무엇을 넣느냐가 곧 타입이에요.

① 이름 규칙

영문자 · 숫자 · _만, 숫자로 시작 불가, 대소문자 구분. 관례는 snake_case(is_free_shipping) — 자바의 camelCase(isFreeShipping)와 반대예요.

② 산술 · 비교 · 논리

7 / 2 → 3.5, 7 // 2 → 3, 7 % 2 → 1, 2 ** 10 → 1024. 비교 == != > < >= <=는 True/False(첫 글자 대문자). and는 둘 다 참, or는 하나라도 참, not은 뒤집기.

☕ 자바에서는

int · floatword[0] · word[-1]word[0:3]f"{x:,}" · f"{x:.2f}"

한 줄 요약문자열은 글자마다 0부터 번호가 있고, 음수 번호는 뒤에서부터 센다. [시작:끝] 슬라이싱은 끝을 포함하지 않는다. 실무 단골 메서드 네 개(strip · split · join · replace)와 f-string 서식(:, · :.2f)이 핵심.

쉽게 말하면"PYTHON"은 번호표 0~5가 붙은 글자 여섯 칸이에요. [-1]은 "뒤에서 첫 칸", [0:3]은 "0번부터 3번 앞까지".

① 인덱싱 · 슬라이싱 · len

word = "PYTHON" → word[0]은 'P', word[-1]은 'N', word[0:3]은 'PYT', len(word)는 6. 문자열은 바꿀 수 없어서(immutable) word[0] = 'J'는 오류이고, 메서드는 모두 새 문자열을 돌려줍니다 — 결과를 변수에 받아야 해요.

② 실전 메서드 넷 + f-string

" Hello ".strip() 앞뒤 공백 제거 · "a,b,c".split(",") → 리스트 · "-".join([...]) 리스트를 이어 붙이기(구분자가 앞에 옴) · .replace("cats", "dogs"). f-string은 f"{price:,}" → 1,234,567, f"{pi:.2f}" → 3.14.

☕ 자바에서는

word.charAt(0) → word[0], word.substring(0, 3) → word[0:3](둘 다 끝 미포함), word.length() → len(word), trim() → strip(), String.join("-", list) → "-".join(list), String.format("%,d", price) → f"{price:,}". 자바엔 음수 인덱스가 없어 word.charAt(word.length() - 1)로 썼던 것이 word[-1] 한 번이에요. 자바의 split은 정규식을 받지만 파이썬 split은 글자 그대로 나눠요.

리스트 · 튜플 · 딕셔너리 — 여러 값 담기, 그리고 "딕셔너리를 담은 리스트"

list [ ]tuple ( )dict { }append · insert · extend · sortenumerate

한 줄 요약리스트는 순서 있고 바꿀 수 있는 목록, 튜플은 바꿀 수 없는 목록, 딕셔너리는 이름표(key)로 값을 꺼내는 짝 모음이다. 딕셔너리 여러 개를 리스트에 담으면 표(행 여러 개)가 된다.

쉽게 말하면리스트는 번호 붙은 서랍, 튜플은 봉인된 서랍, 딕셔너리는 이름표 붙은 서랍이에요. [{…}, {…}]는 엑셀 표 한 장 — 한 줄이 딕셔너리 하나예요.

① 리스트 실전 메서드

append(x) 맨 뒤 추가 · insert(0, x) 위치에 추가 · extend([..]) 여러 개 추가 · index(x) 위치 · count(x) 개수 · sort() 오름차순 정렬. append · insert · extend · sort는 리스트 자체를 바꾸고 None을 돌려줘요 — nums = nums.sort()는 리스트를 잃어버리는 실수예요. 원본을 두고 정렬본만 원하면 sorted(nums).

② 다중 할당 · enumerate · 튜플 · 딕셔너리

a, b = b, a로 임시 변수 없이 맞바꾸기. for i, x in enumerate(목록):은 번호와 값을 함께 꺼내며 번호는 0부터(1부터 원하면 enumerate(목록, 1)). 튜플 (35.2, 128.6)은 수정하면 TypeError — 좌표처럼 바뀌면 안 되는 값에. 딕셔너리는 info["name"]으로 꺼내고 info["age"] = 22로 수정 · 추가. 없는 키를 꺼내면 KeyError, 안전하게는 info.get("키", 기본값).

☕ 자바에서는

조건문 — if · elif · else, 삼항 표현식, 조건 체이닝

if / elif / elseA if 조건 else B80 <= score < 90들여쓰기 4칸

한 줄 요약조건 뒤 콜론(:), 블록은 들여쓰기 4칸. 여러 조건은 위에서부터 차례로 검사해 처음 참인 하나만 실행한다. 값 하나를 고를 땐 삼항 A if 조건 else B, 범위는 80 <= score < 90처럼 이어 쓴다.

쉽게 말하면중괄호 대신 "들여쓰기"가 블록이에요. 들여쓰기가 틀리면 모양만 틀린 게 아니라 프로그램이 다르게 동작하거나 실행이 안 돼요.

① 순서가 중요한 elif

점수 등급은 큰 기준부터 검사해요(>= 90 → >= 80 → >= 70). 72점은 첫 두 조건이 거짓이고 >= 70에서 멈춰 C. 순서를 거꾸로(>= 70을 먼저) 쓰면 95점도 C가 돼요.

② 삼항 · 체이닝 · 논리 결합

status = "성인" if age >= 18 else "미성년" — 순서가 "참일 때 값 → 조건 → 거짓일 때 값". 겹쳐 쓰면 "저체중" if bmi < 18.5 else ("과체중" if bmi >= 25 else "정상"). 80 <= score < 90은 80 <= score and score < 90과 같아요. 조건 여러 개는 or · and로 묶어요.

☕ 자바에서는

한 줄 요약파이썬 for는 언제나 "목록에서 하나씩 꺼내기"이고, 숫자를 세고 싶으면 range(시작, 끝)(끝 미포함)을 목록으로 쓴다. 조건이 참인 동안은 while. 리스트를 만드는 for는 리스트 컴프리헨션 한 줄로 줄인다.

쉽게 말하면[n * n for n in nums if n % 2 == 0]는 "nums에서 n을 하나씩 꺼내, 짝수면, n*n을 담아라"를 그대로 적은 문장이에요.

① range와 while

range(3) → 0, 1, 2 · range(1, 10) → 1~9 · range(0, 10, 2) → 0, 2, 4, 6, 8. while 조건:은 조건을 바꾸는 줄(i += 1)을 빠뜨리면 끝나지 않아요. 파이썬에는 i++가 없어요 — i += 1. break는 반복을 완전히 끝내고, continue는 이번 회차만 건너뛰어요.

② 리스트 컴프리헨션

빈 리스트 → for → append 세 줄이 [식 for 변수 in 목록] 한 줄. 뒤에 if 조건을 붙이면 거르기. 대괄호를 빼고 함수에 넘기면 제너레이터 식이라 리스트를 만들지 않고 바로 계산해요(sum(item["price"] for item in products)). 쓰지 않는 반복 변수는 관례로 _(for _ in range(6)).

☕ 자바에서는

for (int i = 1; i < 10; i++) → for i in range(1, 10):, 향상된 for for (String f : fruits) → for f in fruits:. 리스트 컴프리헨션은 자바 스트림 nums.stream().filter(n -> n % 2 == 0).map(n -> n * n).toList()와 같은 일을 해요 — 순서만 "map 식이 앞, filter가 뒤"로 바뀐 셈이에요.

파일 입출력과 예외처리 — with open · "w"/"r" · encoding · try · except · finally

with open"w" · "r" · "a"encoding="utf-8"ValueErrorfinally

한 줄 요약with open(파일, 모드) as f: 블록이 끝나면 파일이 자동으로 닫힌다. "w"는 새로 만들거나 덮어쓰기, "r"은 읽기(없으면 오류), "a"는 뒤에 이어 쓰기. 한글이 들어가면 encoding="utf-8"을 꼭 적는다. 오류는 try로 감싸 종류별 except로 받고, finally는 항상 실행된다.

쉽게 말하면with는 "다 쓰면 문 닫고 나오기"를 자동으로 해 주는 장치예요. encoding은 "어떤 글자표로 적을지" — 쓸 때와 읽을 때 글자표가 다르면 한글이 깨지거나 오류가 나요.

① 파일 — 쓰기 · 읽기

f.write("…")는 줄바꿈을 붙이지 않아 한 줄씩 저장하려면 f"{score}\n"처럼 \n을 직접 넣어요. 읽기는 f.read()(전체 한 문자열), for line in f:(한 줄씩, 끝에 \n 포함 → line.strip()). 경로를 이름만 쓰면 현재 작업 폴더(노트북은 노트북이 있는 폴더) 기준이에요.

② encoding — 이 PC(3.15)와 교안 권장(3.12)이 다른 곳

교안 코드 open("memo.txt", "w")는 encoding이 없어요. 파이썬 3.15는 기본이 UTF-8이라 오늘은 문제없었지만, 3.12 이하 Windows는 기본이 cp949예요. 직접 비교해 보니 같은 "오늘 수업 완료"가 3.15에선 20바이트(UTF-8), UTF-8 모드를 끈 실행(-X utf8=0, 3.12 이하 Windows와 같은 기본값)에선 14바이트(cp949)로 저장됐고, UTF-8 파일을 cp949로 읽으면 UnicodeDecodeError가 났어요. 내 점수 파일 풀이처럼 encoding="utf-8"을 쓰면 어느 버전 · 어느 PC에서도 같아요.

③ 예외 — 종류별로 받기

int("abc") → ValueError, 10 / 0 → ZeroDivisionError, 없는 파일 "r" → FileNotFoundError, 없는 키 → KeyError. except ValueError:처럼 종류를 적어 받고, 메시지가 필요하면 except ValueError as e:. 그냥 except:는 모든 오류(오타로 난 오류까지)를 삼켜 원인을 숨기니 피하세요.

☕ 자바에서는

with open(…) as f: ≈ try-with-resources try (BufferedReader br = Files.newBufferedReader(path, StandardCharsets.UTF_8)) { … } — 자원을 자동으로 닫는 같은 생각이에요. try · except · finally ≈ try · catch · finally, except ValueError ≈ catch (NumberFormatException e)(Integer.parseInt("abc")). 자바와 달리 파이썬엔 "반드시 잡아야 하는 예외(checked exception)"가 없어 throws도 없어요. 자바 18부터 기본 문자셋이 UTF-8이 된 것(JEP 400)과 파이썬 3.15의 UTF-8 기본값은 같은 흐름이에요.

한 줄 요약Pandas는 표(행 · 열) 데이터를 다루는 라이브러리. 번호표(인덱스)가 붙은 1차원 목록이 Series, Series 여러 개를 열로 모은 2차원 표가 DataFrame. 딕셔너리로 만들면 키가 열 이름, 값 리스트가 그 열의 값이 된다.

① 만들기와 기본 속성

pd.DataFrame({"name": [...], "score": [...]}) — 리스트 길이가 같아야 해요. df.shape는 (행 수, 열 수) 튜플이라 행 수는 df.shape[0](또는 len(df)), df.columns는 열 이름, df.index는 행 번호(기본 0부터 — RangeIndex). 설치는 pip install pandas, 쓸 때는 관례대로 import pandas as pd.

② 이 PC는 pandas 3.0 — 출력 모양이 교안과 조금 다르다

교안은 Index(['name', 'score'])라고 적었지만 실행하면 Index(['name', 'score'], dtype='str')가 나와요. pandas 3.0부터 글자 열이 전용 문자열 자료형(str)이 됐기 때문이에요(2.x에서는 object). type(df["score"])도 pandas.Series로 짧게 보여요. 선생님 노트북(파이썬 3.14)도 같은 모양이라 같은 pandas 3 계열로 보입니다.

DataFrame ≈ 테이블 한 개(SELECT 결과), 열 이름 ≈ 컬럼, 인덱스 ≈ 행 번호(기본키처럼 쓸 수도 있음). 자바로는 List<Map<String, Object>>나 DTO 리스트 — MyBatis가 돌려주던 List<BoardDto>가 한 표예요. 다른 점은 Pandas는 열 단위로 저장해서 "점수 열 전체의 평균"을 반복문 없이 바로 구한다는 것.

개념 10 · Day 3

CSV · JSON 읽고 쓰기 — to_csv(index=False), force_ascii=False, utf-8-sig

to_csv · read_csvto_json · read_jsonindex=Falseforce_ascii=Falseorient="records"

한 줄 요약df.to_csv("파일.csv", index=False)로 저장하고 pd.read_csv("파일.csv")로 읽는다. JSON은 to_json · read_json. index=False를 빼면 행 번호가 열로 같이 저장되고, JSON은 force_ascii=False를 빼면 한글이 연…로 저장된다.

쉽게 말하면CSV는 "쉼표로 칸을 나눈 메모장 표", JSON은 "중괄호로 이름표를 붙인 데이터"예요. 둘 다 사람이 메모장으로 열어 읽을 수 있어서 프로그램끼리 주고받기 좋아요.

① index=False — 왜 빼먹으면 안 되나

그냥 to_csv하면 맨 앞에 이름 없는 행 번호 열이 생기고, 다시 읽으면 Unnamed: 0이라는 쓸모없는 열이 붙어요(아래 실행 결과). 교안 8쪽 Tip 그대로예요.

② JSON의 한글과 모양

to_json은 기본으로 한글을 연필처럼 바꿔 저장해요(파이썬이 읽으면 다시 한글이 되지만 사람이 보기 어렵다). force_ascii=False면 한글 그대로. 기본 모양(orient="columns")은 {"item": {"0": "연필", …}}처럼 열 → 행 번호 → 값이고, orient="records"면 [{"item": "연필", "price": 500}, …] — 어제 배운 "딕셔너리를 담은 리스트"이자 REST API가 주고받는 모양이에요. 실습 폴더의 students.json(옵션 없음)과 items.json(force_ascii=False)이 바로 이 차이예요.

③ 엑셀에서 열 CSV는 utf-8-sig

Pandas의 CSV는 UTF-8로 저장되는데, Windows 엑셀은 BOM(파일 맨 앞 표시 3바이트) 없는 UTF-8 CSV의 한글을 깨뜨려 여는 경우가 많아요. 내 Day 3 종합 풀이처럼 encoding="utf-8-sig"로 저장하면 BOM이 붙어 엑셀에서도 한글이 보여요(실습 폴더 result.csv의 첫 3바이트 EF BB BF 확인). 파이썬끼리만 주고받으면 그냥 UTF-8이면 돼요.

② 조건 여러 개 — and 가 아니라 &

df[(df["score"] >= 70) & (df["score"] < 90)] — 행마다 비교하는 조건은 &(그리고) · |(또는) · ~(아님)을 쓰고 조건마다 괄호를 쳐요. 파이썬 and를 쓰면 "True/False 목록 전체가 참이냐"를 물어 ValueError가 나요(로컬 확인).

③ loc 과 iloc

df.iloc[0] 0번째 행(위치), df.loc[0, "name"] 인덱스가 0인 행의 name. 기본 인덱스(0, 1, 2…)에서는 둘이 같아 보이지만 슬라이싱 끝이 달라요 — loc[0:1]은 1을 포함(2행), iloc[0:1]은 파이썬처럼 미포함(1행). 필터링 뒤처럼 인덱스가 0, 1, 3으로 듬성해지면 차이가 더 커져요.

🗄️ SQL · 자바로는

df[["name", "score"]] = SELECT name, score, df[df["score"] >= 80] = WHERE score >= 80, & · | = AND · OR, head(5) = LIMIT 5, describe() ≈ COUNT · AVG · MIN · MAX를 한 번에. 자바라면 list.stream().filter(s -> s.getScore() >= 80). tolist()는 Series를 파이썬 리스트로 — 자바의 .toList()와 같은 역할이에요(to_list()도 같은 함수).

개념 12 · Day 3

데이터 정제 — isna · fillna · dropna · drop_duplicates, rename · drop · apply(lambda)

NaNfillna(0)drop_duplicates(subset, keep)rename · dropapply(lambda)다시 담기

한 줄 요약빈 값(NaN)은 isna()로 찾고 fillna(값)으로 채우거나 dropna()로 지운다. 중복 행은 drop_duplicates() — 기본은 모든 열이 같은 행만, 특정 열 기준이면 subset=[…]. 열 이름 바꾸기 rename, 지우기 drop, 조건으로 새 열은 apply(lambda x: …). 이 메서드들은 새 표를 돌려주므로 다시 담아야 한다.

쉽게 말하면df.fillna(0)은 "0으로 채운 복사본을 보여 줘"예요. 원본은 그대로라 df = df.fillna(0)처럼 받아 둬야 다음 줄에서도 채워진 표를 써요.

① 결측치

None을 넣으면 Pandas는 NaN(Not a Number)으로 바꾸고, 숫자 열은 실수(float64)가 돼요 — 그래서 88이 88.0으로 보여요. df.isna().sum() 열마다 빈 칸 수, fillna(0) 채우기, dropna() 빈 칸이 있는 행 지우기. 무엇으로 채울지(0? 평균?)는 데이터의 뜻에 따라 정해요 — 시험을 안 본 학생을 0점으로 채우면 평균이 내려가요.

② 중복 — 무엇이 "같은 행"인가

Day 3 종합에서 영희가 0.0과 95.0 두 번 나오는데 drop_duplicates()는 지우지 않아요 — 점수가 달라 같은 행이 아니니까요. 이름 기준이면 drop_duplicates(subset=["name"], keep="last")(마지막 것을 남김, 기본은 "first"). 이 풀이는 내 노트북과 선생님 노트북에 똑같이 들어 있어요.

③ apply와 lambda — 그리고 NaN의 함정

df["score"].apply(lambda x: "A" if x >= 90 else "B")는 점수 하나하나를 x로 받아 결과를 모은 새 열이에요. lambda는 이름 없는 한 줄 함수(자바의 람다 x -> …). 주의: 점수가 NaN이면 NaN >= 90이 거짓이라 "B"가 나와요([95, None] → ['A', 'B'], 로컬 확인). 결측치를 먼저 처리하고 apply 하세요.

🗄️ SQL · 자바로는

isna() = IS NULL, fillna(0) = COALESCE(score, 0) · IFNULL, dropna() = WHERE score IS NOT NULL, drop_duplicates() = SELECT DISTINCT *, rename = AS, drop(columns=…) = 그 열을 SELECT에서 빼기, apply(lambda …) = CASE WHEN score >= 90 THEN 'A' ELSE 'B' END. "새것을 돌려준다"는 자바 String 메서드(trim()이 원본을 안 바꿈)와 같은 성질이에요.

개념 13 · Day 4

NumPy — 배열 통째로 계산하기, 조건 필터링, 그리고 표준편차 두 가지

np.arrayarr * 2 · arr + 5arr[arr >= 80]mean · max · sumnp.std ddof

한 줄 요약np.array([…])는 숫자 계산용 배열. 연산을 원소 하나하나에 한꺼번에 적용한다(arr + 5, arr * 2). 비교식 arr >= 80은 True/False 배열이 되고, 그걸 대괄호에 넣으면 조건에 맞는 값만 남는다. Pandas의 열도 속은 NumPy 배열(df["score"].values).

쉽게 말하면파이썬 리스트에 * 2를 하면 목록이 두 번 이어 붙고, NumPy 배열에 * 2를 하면 숫자마다 두 배가 돼요. "목록"이 아니라 "숫자 묶음"이라서요.

① 벡터 연산과 불리언 인덱싱

[88, 92] * 2 → [88, 92, 88, 92](리스트 반복), np.array([88, 92]) * 2 → [176 184]. scores[scores >= 80]은 Pandas의 df[df["score"] >= 80]과 같은 생각이에요. 배열에는 한 가지 자료형만 들어가요(정수와 실수를 섞으면 실수로).

② 표준편차 — describe 는 13.70, np.std 는 12.25

Day 4 종합 실습에서 같은 점수 [88, 95, 60, 72, 81]의 표준편차가 두 값으로 나와요. Pandas describe() · Series.std()는 표본 표준편차(n − 1로 나눔, ddof=1)가 기본, NumPy np.std는 모집단 표준편차(n으로 나눔, ddof=0)가 기본이에요. np.std(a, ddof=1)이면 13.70으로 같아져요(로컬 확인). 둘 다 틀린 게 아니라 정의가 달라요.

☕ 자바로는

자바 int[]에 5를 더하려면 for (int i = 0; i < a.length; i++) a[i] += 5;, 80점 이상만 모으려면 반복문 + ArrayList, 평균은 Arrays.stream(a).average(). NumPy는 이 반복문을 C로 짠 내부 코드가 대신 돌려서 짧고 빨라요 — 자바 스트림의 map · filter · sum을 연산자 하나로 쓰는 느낌이에요.

FastAPI 시작 — 데코레이터 하나가 API 하나, uvicorn으로 실행, /docs 자동 문서

pip install fastapi uvicorn@app.getuvicorn main:app --reloadSwagger /docsJSON 응답

한 줄 요약FastAPI는 파이썬으로 API 서버를 만드는 웹 프레임워크. app = FastAPI()에 @app.get("/경로")를 붙인 함수를 만들면 그 주소의 요청을 처리하고, 돌려준 딕셔너리 · 리스트 · Pydantic 객체가 JSON으로 나간다. 서버 실행은 uvicorn, 문서와 시험 화면은 /docs에 저절로 생긴다.

쉽게 말하면FastAPI는 "어느 주소로 오면 어느 함수를 부를지" 적어 둔 안내판이고, uvicorn은 그 안내판을 들고 문 앞에 서서 실제로 손님(요청)을 받는 사람이에요.

① 설치와 실행

교안 순서는 가상환경(python -m venv myenv → myenv\Scripts\activate) 안에서 pip install fastapi uvicorn. 실행은 uvicorn main:app --reload — main은 파일 이름, app은 FastAPI 객체 변수, --reload는 코드를 저장하면 서버를 다시 띄워 줘요. uvicorn 명령을 못 찾으면 python -m uvicorn main:app --reload(선생님 파일 첫 줄 주석). 기본 주소는 http://127.0.0.1:8000.

② 데코레이터 — 함수 위의 @

@app.get("/")는 "아래 함수를 GET / 처리기로 등록해 줘"라는 뜻이에요. 데코레이터는 함수를 받아 무언가를 덧붙이는 파이썬 문법이고, 등록은 파일이 위에서 아래로 읽힐 때 순서대로 일어나요 — 그래서 경로를 쓰는 순서가 의미를 가져요(py-17).

③ /docs — 코드가 곧 문서

FastAPI는 함수의 경로 · 매개변수 · 타입 힌트 · Pydantic 모델을 읽어 OpenAPI 명세(/openapi.json)를 만들고, /docs(Swagger UI)와 /redoc에 보여 줘요. "Try it out"으로 값을 넣어 바로 요청을 보낼 수 있어 Postman 없이 시험할 수 있어요. 함수 이름은 문서의 이름(operationId)에도 쓰여서, 같은 경로를 두 번 등록하면 Duplicate Operation ID 경고가 나요.

☕ 스프링으로는

@app.get("/") ≈ @GetMapping("/"), app = FastAPI() ≈ @SpringBootApplication + 내장 톰캣, uvicorn ≈ 톰캣(실제로 요청을 받는 서버), --reload ≈ Spring DevTools. 돌려준 딕셔너리가 JSON이 되는 건 @RestController + Jackson과 같은 일이에요. 스프링에서 Swagger를 보려면 springdoc 의존성을 따로 넣어야 했는데, FastAPI는 처음부터 들어 있어요. → 백엔드 web-85 REST API

경로(Path) 파라미터 — 타입 힌트로 변환 · 검증, 422, 고정 경로를 먼저

/items/{item_id}item_id: int422경로 순서/students/{grade}/{number}

한 줄 요약주소 안의 {이름} 자리 값은 같은 이름의 함수 매개변수로 들어온다. 타입 힌트를 int로 주면 FastAPI가 글자를 정수로 바꾸고, 바꿀 수 없으면(/items/abc) 함수를 부르지 않고 422를 돌려준다. 경로는 등록한 순서대로 맞춰 보므로 /users/me 같은 고정 경로를 /users/{user_id}보다 위에 쓴다.

쉽게 말하면우체국이 주소를 위에서부터 차례로 맞춰 보는 거예요. "OO동 아무 번지"를 먼저 붙여 두면 "OO동 동사무소"로 온 편지도 거기로 가 버려요. 특별한 주소를 먼저 붙여 둬야 해요.

① 타입 힌트 = 변환 + 검증

URL은 원래 다 글자예요. item_id: int라고 쓰면 "3"을 3으로 바꿔 주고, "abc"면 {"detail":[{"type":"int_parsing","loc":["path","item_id"], …}]}와 함께 422. 어느 자리(loc)의 무엇이 틀렸는지 응답에 적혀 있어요. 타입을 str로 두면 무엇이든 통과해요 — 내 도전 풀이의 grade: str은 /students/two/15/score도 받아요(문제는 정수).

② 순서 — 고정 경로를 위에

/v2/users/{user_id}를 먼저, /v2/users/me를 나중에 등록하고 /v2/users/me를 부르면 첫 번째에 걸려 "me"를 정수로 바꾸려다 422예요(로컬 확인). 순서를 바꾸면 200. 교안 9쪽 2번이 바로 이 연습이고, 내 풀이는 /courses/popular를 /courses/{course_id}보다 위에 써서 맞아요.

☕ 스프링으로는

@GetMapping("/items/{itemId}") … (@PathVariable int itemId)와 같아요. 스프링에서는 abc를 int로 못 바꾸면 400(Bad Request)이 나는 것이 기본인데, FastAPI는 422로 "형식은 맞는데 내용을 처리할 수 없다"고 답해요. 순서 문제는 스프링에선 덜 생겨요 — 스프링은 등록 순서가 아니라 더 구체적인 패턴(/users/me)을 먼저 고르기 때문이에요.

쿼리(Query) 파라미터 — ?key=value, 기본값이 있으면 선택, bool 파싱, Path와 섞기

/search?keyword=python&limit=3limit: int = 5필수 · 선택show_tax: bool

한 줄 요약경로에 없는 매개변수는 모두 쿼리 파라미터(? 뒤 key=value). 기본값이 없으면 필수(빠지면 422), 있으면 선택. bool은 true/false · 1/0 · yes/no를 알아듣는다. 한 함수에 경로 · 쿼리를 자유롭게 섞어 쓴다.

쉽게 말하면경로는 "어느 가게"이고 쿼리는 주문서의 옵션 칸이에요. "할인 몇 %?", "세금 포함?" 같은 선택 사항을 적되, 비워 두면 기본값으로 처리해요.

① 필수와 선택

def search_items(keyword: str, limit: int = 5) — /search?keyword=python&limit=3이면 3, limit을 빼면 5, keyword를 빼면 {"type":"missing","loc":["query","keyword"]}로 422. limit=many처럼 타입이 틀려도 422예요(모두 로컬 확인).

② bool 쿼리 — 무엇을 참으로 보나

show_tax: bool = False에 true · 1 · yes · on을 보내면 참, false · 0 · no · off는 거짓, maybe 같은 값은 422(모두 로컬 확인). 교안 12쪽 2번이 이것 — 참이면 응답 딕셔너리에 "tax_included": True를 더하는 조건문이에요.

한 줄 요약POST · PUT은 데이터를 주소가 아니라 요청 본문(JSON)으로 보낸다. class Member(BaseModel)로 필드와 타입을 적고 함수 매개변수를 member: Member로 두면, FastAPI가 JSON을 읽어 검사 · 변환한 객체를 넘겨준다. 기본값이 없는 필드는 필수, Optional[str] = None은 없어도 되는 필드. 딕셔너리로 바꿀 땐 model_dump().

쉽게 말하면BaseModel은 "가입 신청서 양식"이에요. 이름 · 나이 · 동아리는 꼭 적어야 하고 전화번호는 비워도 되는 양식을 먼저 만들어 두면, 빈칸이 있거나 나이에 글자를 쓴 신청서는 접수 창구(FastAPI)에서 바로 돌려보내요(422).

① 검사와 변환

{"name": "홍길동", "age": "22"}처럼 숫자를 글자로 보내도 바꿀 수 있으면 age=22로 받아 줘요. "스물"이면 int_parsing, age를 빼면 missing으로 422 — 응답의 loc이 ["body","age"]예요. 모델에 없는 필드("hobby")는 오류 없이 버려져요(기본 설정). JSON이 아닌 폼 형식으로 보내도 422예요(모두 로컬 확인).

② Optional과 model_dump

한 줄 요약메서드가 곧 행위 — GET 조회, POST 생성, PUT 수정, DELETE 삭제. 찾는 자원이 없으면 raise HTTPException(status_code=404, detail="…")로 그 자리에서 응답을 끝낸다({"detail": "…"}). 타입 오류 422는 FastAPI가 자동으로, 404처럼 뜻이 담긴 실패는 내가 직접. 그리고 같은 메서드 + 같은 경로는 한 번만 등록한다.

쉽게 말하면raise HTTPException은 "죄송합니다, 그런 상품은 없어요" 안내문을 들고 바로 손님을 돌려보내는 것이에요. 아래 코드는 실행되지 않아요.

① 상태 코드 — 누가 정하나

성공은 기본 200. 생성(POST)을 201로 알리려면 @app.post("/members", status_code=201)(로컬에서 201 Created 확인 — 교안 · 실습은 기본 200). 실패: 형식 오류 422(자동), 없는 주소 404(자동), 주소는 있는데 메서드가 없음 405(자동), 없는 자원 404는 직접 HTTPException으로.

② 같은 경로를 두 번 — 먼저 등록된 것이 이긴다

한 파일에 실습을 이어 풀다 보면 @app.get("/products/{product_id}")가 여러 번 생겨요. FastAPI는 등록 순서대로 맞춰 보므로 첫 번째만 응답하고 나머지는 죽은 코드가 돼요. 오류로 멈추지 않아 놓치기 쉽고, 단서는 /openapi.json을 만들 때의 Duplicate Operation ID 경고와 문서(/docs)에 GET이 하나뿐인 것이에요. 선생님처럼 실습마다 경로를 나누거나(/products17/…), 실습마다 파일을 나눠요.

☕ 스프링으로는

HTTPException(404) ≈ throw new ResponseStatusException(HttpStatus.NOT_FOUND, "…") 또는 ResponseEntity.notFound(), status_code=201 ≈ ResponseEntity.status(201). 백엔드 12번 예제는 없는 글에도 200 {"dto":null}을 줬는데(web-85), 오늘 실습은 404를 직접 돌려줘 그 "고칠 곳"을 해결한 모양이에요. 같은 경로 중복은 스프링이라면 서버가 아예 안 뜨는 오류(Ambiguous mapping)라 바로 알 수 있는데, FastAPI는 조용히 첫 번째를 써요.

FastAPI + DB — SQLAlchemy ORM, Depends(get_db), 요청 · 응답 스키마 분리, Field 검증

create_engine · sessionmakerclass Product(Base)Depends(get_db)response_modelField(ge=0, max_length=100)201

한 줄 요약SQLAlchemy는 파이썬 클래스와 DB 테이블을 짝지어 SQL 대신 객체로 다루게 해 주는 ORM. Product(Base)가 products 테이블, db.add · commit · refresh가 INSERT, db.query(Product).filter(…).first()가 SELECT. 요청마다 세션은 Depends(get_db)가 열고 닫는다. 응답은 response_model=ProductResponse로 모양을 고정하고, 입력 범위는 Field(ge=0, max_length=100)로 검사한다.

쉽게 말하면어제는 상품을 파이썬 딕셔너리(서버를 끄면 사라지는 메모장)에 적었고, 오늘은 진짜 창고(DB)에 넣었어요. 창고 직원(세션)은 손님(요청)마다 한 명씩 나왔다가, 일이 끝나면 돌아가요.

① 연결 · 모델 · 세션

create_engine("mysql+pymysql://계정:비밀번호@localhost:3306/test")로 DB 연결(드라이버 PyMySQL), sessionmaker로 세션 공장, Base.metadata.create_all(engine)은 테이블이 없으면 CREATE TABLE. echo=True면 실행되는 SQL이 콘솔에 찍혀요 — 스프링의 show-sql처럼. 수정은 객체 속성을 바꾸고 commit()하면 바뀐 열만 UPDATE해요(로그에서 UPDATE products SET name=?, price=?, stock=? — 같은 값인 in_stock은 빠짐).

② Depends(get_db) — 의존성 주입

def get_db(): db = SessionLocal(); try: yield db; finally: db.close()를 만들어 두고 처리 함수 매개변수에 db: Session = Depends(get_db)를 적으면, FastAPI가 요청마다 세션을 만들어 넣어 주고 응답 뒤 finally에서 닫아요. yield 덕분에 "앞부분 = 준비, 뒷부분 = 정리"가 한 함수에 들어가요.

③ 스키마 분리와 검증

요청용(ProductCreate · ProductUpdate)과 응답용(ProductResponse — id 포함)을 나누고, 응답 모델에 model_config = ConfigDict(from_attributes=True)를 두면 ORM 객체를 그대로 return해도 JSON으로 바뀌어요. Field(ge=0)은 음수 가격을, max_length=100은 101자 이름을 422로 막아요(로컬 확인 — DB 열 길이 String(100)과 맞춘 것).

☕ 스프링으로는

SQLAlchemy ORM ≈ JPA(Hibernate) — MyBatis처럼 SQL을 직접 쓰지 않고 객체로 다뤄요.           status_code=status.HTTP_201_CREATED)             # ← 생성은 201
def create_product(product: ProductCreate, db: Session = Depends(get_db)):
    db_product = Product(**product.model_dump())          # ← 요청 스키마 → ORM 객체
    db.add(db_product)
    db.commit()                                           # ← INSERT 확정
    db.refresh(db_product)                                # ← DB가 만든 id 를 다시 읽음
    return db_product                                     # ← ORM 객체 → ProductResponse

@app.get("/products/{product_id}", response_model=ProductResponse)
def get_product(product_id: int, db: Session = Depends(get_db)):

    if not db_product:
        raise HTTPException(status_code=404, detail=f"상품 ID {product_id}번을 찾을 수 없습니다.")

개념 22 · Day 6

LLM과 Agent — 다음 토큰 예측, 다섯 가지 한계, Chain과 Agent의 차이

토큰컨텍스트 윈도우환각Tool Calling생각 → 행동 → 관찰

한 줄 요약LLM은 방대한 글로 학습해 다음에 올 토큰을 확률로 예측하며 문장을 이어 쓰는 모델. 그래서 그럴듯한 거짓(환각) · 학습 이후 정보 없음 · 계산 약함 · 기억 없음 · 직접 행동 불가라는 한계가 있다. 여기에 Tool(손발) · Memory(기억) · 근거 문서(RAG)를 붙여 스스로 다음 행동을 고르게 만든 것이 AI Agent.

쉽게 말하면LLM은 아주 거대한 "자동 완성"이에요. 아는 걸 꺼내는 게 아니라 패턴으로 이어 쓰기 때문에, 틀린 말도 자신 있게 써요. Chain은 레시피대로 따라 하는 요리, Agent는 냉장고를 보고 메뉴를 정하는 요리사예요(교안 비유).

① 한계 → 보완 (교안 개념 추가본 5쪽)

환각 → 근거 문서 함께 주기(RAG, Day 8) · 최신 정보 없음 → 검색 · API 도구 · 계산 약함 → 계산 도구 · 기억 없음 → 대화 기록(Memory) · 직접 행동 불가 → 함수를 도구로 연결. 한 번에 읽을 수 있는 길이(컨텍스트 윈도우)에도 한계가 있어 대화 기록을 무한히 쌓을 수는 없어요.

② Tool Calling — LLM은 도구를 직접 실행하지 않는다

Agent는 "생각 → 행동(도구 호출 요청) → 관찰(결과 확인)"을 정보가 충분할 때까지 반복해요. 이때 LLM이 돌려주는 건 "get_weather(city="서울")를 불러 줘"라는 요청서(tool_calls)뿐이고, 실제 실행은 우리 코드가 한 뒤 결과를 다시 LLM에 넘겨요. 오늘 종합 실습은 이 과정을 사람(코드)이 직접 했어요 — 계산은 calculate로, 결과를 질문에 넣어 체인으로(실습 33). LLM이 스스로 고르는 건 Day 9 Agent.

☕ 앞 과정으로는

Chain은 지금까지 짠 프로그램처럼 순서가 고정(Controller → Service → Mapper)이고, Agent는 실행 중에 LLM이 분기를 고르는 프로그램이에요. 그래서 Agent에는 "어떤 도구를 줄지 · 몇 번까지 반복할지 · 어떤 규칙을 지킬지(system 프롬프트)"를 설계하는 일이 생겨요 — 스프링에서 인터셉터 · 권한 검사로 "무엇을 허락할지" 정하던 것과 닮았어요.

핵심 정리
  • LLM = 다음 토큰 확률 예측 → 그럴듯하지만 틀릴 수 있다(환각).
  • 한계 다섯: 환각 · 최신 정보 · 계산 · 기억 · 행동 — RAG · Tool · Memory로 보완.
  • Agent = LLM(두뇌) + Tool(손발) + Memory(기억) + Prompt(역할), 생각 → 행동 → 관찰 반복.
  • LLM은 도구 "호출 요청"만, 실행은 내 코드.

LLM은 숫자를 계산하지 않고 그럴듯한 다음 글자를 이어 써서 큰 수 계산이 틀리기 쉬워요. 계산 도구(calculate)로 정확히 계산하고 결과만 LLM에게 설명시키는 것이 오늘 종합 실습의 구조예요.
Chain과 Agent 중 "어떤 질문이 와도 요약 → 번역" 작업에 맞는 것은?

💼 실무에서는"이건 LLM이 판단할 일인가, 코드로 정해 둘 일인가"를 먼저 나눠요. 정해진 흐름은 Chain(싸고 예측 가능), 열린 질문은 Agent(유연하지만 비용 · 오류 가능성 큼). 그리고 LLM 답은 항상 검증할 수 있는 근거(RAG 출처 · 도구 결과)와 함께 보여 주는 것이 신뢰의 기본이에요.

한 줄 요약프롬프트에서 바뀌는 부분만 {food}처럼 비워 둔 틀이 PromptTemplate. template | llm | StrOutputParser()처럼 파이프(|)로 이어 붙인 것이 체인(LCEL)이고, chain.invoke({"food": "김치"}) 한 번에 틀 채우기 → 모델 호출 → 글자만 꺼내기가 차례로 일어난다. 한 체인의 출력을 다음 체인의 입력으로 넘기면 여러 단계 작업이 된다.

쉽게 말하면레고 블록 세 개(주문서 양식 → 요리사 → 접시에 담기)를 일렬로 끼운 컨베이어 벨트예요. 맨 앞에 재료({"food": "김치"})를 넣으면 맨 끝에서 글자가 나와요.

① 틀이 하는 일 — 변수 검사

PromptTemplate.from_template("{food}의 유래를 한 문장으로 알려줘")는 변수 목록(input_variables = ['food'])을 알아요. {"dish": …}처럼 이름을 틀리면 LLM을 부르기 전에 KeyError: Input to PromptTemplate is missing variables {'food'}(로컬 확인) — 돈 쓰기 전에 실수를 잡아 줘요.

② parser가 있고 없고

prompt | llm까지만 하면 결과가 AIMessage 객체(글자는 .content)이고, | StrOutputParser()를 붙이면 바로 문자열이 나와요(가짜 모델로 확인 — 이 버전에서는 str을 상속한 TextAccessor라는 이름으로 보이지만 문자열 그대로 쓸 수 있어요). 그래서 체인의 끝에 파서를 두면 다음 체인 · 파이썬 코드에 넘기기 쉬워요.

③ 체인 두 개 잇기 (교안 14쪽)

summary = summarize_chain.invoke({"text": long_text}) → translate_chain.invoke({"text": summary}). 앞 체인의 출력(문자열)을 뒤 체인의 입력 변수에 넣으면 "요약 → 번역" 같은 여러 단계 작업이 돼요. 내 노트북도 그대로 동작해 한 줄 요약과 영어 번역이 저장돼 있어요.

☕ 앞 과정으로는

PromptTemplate ≈ String.format("%s의 유래…", food)나 MyBatis의 #{food} — 틀은 고정, 값만 바꿔 끼워요. 파이프 | ≈ 자바 스트림의 .map(…).map(…), 또는 리눅스의 cat | grep. 체인은 Controller → Service → Mapper처럼 순서가 정해진 처리 흐름이에요.

LLM 답의 내용(예: 초밥의 기원 설명)은 사실 확인을 하지 않았어요 — LLM은 그럴듯하게 틀릴 수 있어요(py-22). 교안 2번은 food="김치"였는데 노트북은 "초밥"으로 불렀어요(실습 30).
핵심 정리
  • 바뀌는 곳만 {변수} — from_template, 변수 누락은 호출 전에 오류.
  • prompt | llm | StrOutputParser() → .invoke({변수: 값}) → 문자열.
  • parser 없으면 AIMessage(.content).
  • 앞 체인 출력 → 뒤 체인 입력으로 여러 단계.

@tool — 함수를 LLM이 쓸 수 있는 도구로, docstring이 설명, 그리고 eval의 위험

from langchain_core.tools import tool.name · .description · .argstool.invoke({…})eval 주의

한 줄 요약일반 파이썬 함수 위에 @tool을 붙이면 LLM이 쓸 수 있는 도구 객체(StructuredTool)가 된다. 함수 이름이 .name, docstring이 .description, 매개변수 타입이 .args(입력 형식)가 되어 LLM은 이 설명을 보고 언제 · 어떻게 쓸지 정한다. 호출은 calculate.invoke({"expression": "3*4+2"})처럼 딕셔너리로.

쉽게 말하면도구 상자의 공구마다 이름표와 사용 설명서를 붙이는 거예요. LLM은 공구를 직접 들지 못하고 설명서만 읽고 "이 공구를 이렇게 써 줘"라고 부탁해요. 설명서(docstring)가 엉터리면 엉뚱한 공구를 고르게 돼요.

① 이름 · 설명 · 입력 형식

calculate.args → {'expression': {'title': 'Expression', 'type': 'string'}}, 섭씨 변환 도구(celsius: float)는 'type': 'number'. 잘못된 인자 이름({"expr": …})은 ValidationError로 막혀요 — FastAPI의 Pydantic 검사와 같은 원리예요(py-19). 반환은 문자열로 맞추면 LLM에게 다시 넘기기 편해요(선생님 주석: "LLM이 결과를 받아서 사용해야 되니깐 항상 문자열로").

② eval() — 아무 코드나 실행한다

eval(expression)은 사칙연산만이 아니라 파이썬 식이면 무엇이든 실행해요. 같은 도구에 "__import__('platform').python_version()"을 넣으면 3.15.0이 나와요(로컬 확인 — 무해한 예). Agent가 되어 LLM이 만든 글자가 그대로 들어가면 파일 삭제 · 키 읽기 같은 일도 가능해져요. 선생님도 "보안상 위험하기 때문에 사용을 권장하지 않는다"고 주석을 남겼어요. 숫자와 + - * /만 허용하는 계산기는 ast로 식을 분석해 만들 수 있어요(아래 코드 — 같은 입력이 "허용되지 않은 식"으로 막힘).

☕ 앞 과정으로는

@tool ≈ REST API를 Swagger 문서와 함께 공개하는 것 — 이름 · 설명 · 입력 스키마를 보고 호출하는 쪽이 사용법을 알아요. LLM은 그 "호출하는 쪽"이에요. eval 위험은 SQL 인젝션과 같은 이야기예요 — 밖에서 온 글자를 코드로 실행하면 안 된다(MyBatis ${}를 피하고 #{}를 쓰던 이유).

PYTHON교안 12쪽 도구 (내 풀이) + eval 대신 쓸 수 있는 안전한 계산기 (정리하며 작성)
from langchain_core.tools import tool

@tool
def calculate(expression: str) -> str:
    """사칙연산 수식 문자열(예: '3*4+2')을 계산해 결과를 문자열로 반환합니다."""
    try:
        return str(eval(expression))        # ← 무엇이든 실행 — 주의
    except Exception as e:
        return f"계산 오류: {e}"

# ---- 숫자와 + - * / 만 허용하는 계산 (ast 로 식을 해석) ----
import ast, operator
OPS = {ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul,
       ast.Div: operator.truediv, ast.USub: operator.neg}
def safe_eval(expr):
    def ev(n):
        if isinstance(n, ast.Expression): return ev(n.body)
        if isinstance(n, ast.Constant) and isinstance(n.value, (int, float)): return n.value
        if isinstance(n, ast.BinOp) and type(n.op) in OPS: return OPS[type(n.op)](ev(n.left), ev(n.right))
        if isinstance(n, ast.UnaryOp) and type(n.op) in OPS: return OPS[type(n.op)](ev(n.operand))
        raise ValueError("허용되지 않은 식")
    return ev(ast.parse(expr, mode="eval"))

한 줄 요약LLM 호출은 매번 독립(stateless)이라 앞 대화를 모른다. 그래서 ChatPromptTemplate에 MessagesPlaceholder(variable_name="history") 자리를 만들고, 한 턴이 끝날 때마다 history.append(HumanMessage(…)) · history.append(AIMessage(…))로 내가 직접 기록해 다음 호출에 통째로 넣는다. 기록이 길수록 보내는 토큰 = 비용이 늘어난다.

쉽게 말하면LLM은 매번 처음 보는 상담원이에요. 그래서 상담원을 부를 때마다 "지금까지 나눈 대화 기록지"를 같이 건네줘야 이어서 대답해요. 기록지는 자동으로 써지지 않아서 대화가 끝날 때마다 내가 적어 넣어야 해요.

① 메시지의 모양

("system", "너는 친절한 수학 선생님이야.") · MessagesPlaceholder("history") · ("human", "{input}")로 만든 프롬프트에 history가 비어 있으면 실제로 보내는 메시지는 [SystemMessage, HumanMessage], 한 턴을 쌓은 뒤엔 [SystemMessage, HumanMessage, AIMessage, HumanMessage](가짜 입력으로 확인). history를 아예 안 넘기면 KeyError.

② 직접 쌓기 · 비용 · 다음 단계

history는 자동으로 쌓이지 않아요(교안 15쪽). 턴마다 2개씩 늘어 10턴이면 20개를 매번 다시 보내니, 오래된 대화는 요약하거나 최근 몇 턴만 남겨요(교안 16쪽). LangChain에는 이 일을 대신하는 InMemoryChatMessageHistory, Day 10의 체크포인터(thread_id)가 있어요.

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.output_parsers import StrOutputParser
from langchain_core.messages import HumanMessage, AIMessage      # ← 쓰는 칸에서 import

prompt = ChatPromptTemplate.from_messages([
    ("system", "너는 친절한 친구야."),
    MessagesPlaceholder(variable_name="history"),
    ("human", "{question}"),
])
chain = prompt | llm | StrOutputParser()
history = []

q1 = "내 이름은 하윤이야"
a1 = chain.invoke({"history": history, "question": q1})
history.append(HumanMessage(content=q1))
history.append(AIMessage(content=a1))

a2 = chain.invoke({"history": history, "question": "내 이름이 뭐라고 했지?"})
print(a2)
